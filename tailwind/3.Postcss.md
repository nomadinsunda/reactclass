# 🧪 PostCSS

## CSS를 “해석”하는 도구가 아니라, **CSS를 변환하는 플랫폼**

프론트엔드 빌드 파이프라인을 공부하다 보면
`postcss.config.js`, `autoprefixer`, `tailwindcss`, `cssnano` 같은 이름이 계속 등장합니다.

이때 많은 분들이 PostCSS를 처음 보고 이렇게 생각하십니다.

> “Sass 비슷한 건가?”
> “CSS 전처리기야?”
> “그냥 prefix 붙여주는 라이브러리 아니야?”

결론부터 말씀드리면, **PostCSS는 특정 문법 하나를 제공하는 전처리기라기보다, CSS를 AST로 파싱한 뒤 플러그인으로 변환하는 ‘플랫폼’** 에 가깝습니다. 공식 문서도 PostCSS를 “JavaScript 플러그인으로 스타일을 변환하는 도구”로 설명하고 있으며, 오토프리픽싱, 미래 CSS 문법 변환, 린팅, 최적화 등 수많은 작업을 플러그인으로 수행할 수 있다고 안내합니다. ([GitHub][1])

---

# 🎯 1. PostCSS란 무엇인가?

PostCSS는 **CSS를 입력으로 받아 파싱하고**, 그 결과를 **AST(Abstract Syntax Tree)** 형태로 다룬 다음, **플러그인들이 그 AST를 수정**해서 최종 CSS를 출력하는 도구입니다. 공식 아키텍처 문서도 PostCSS를 CSS 조작 도구를 만들기 위한 프레임워크 성격으로 설명하며, 핵심은 “문법을 정의하고 플러그인으로 변환을 수행하는 것”이라고 말합니다. ([PostCSS][2])

즉, 흐름은 대략 이렇습니다.

```text
원본 CSS
   ↓
파싱(parse)
   ↓
AST 생성
   ↓
플러그인들이 AST 탐색/수정
   ↓
문자열 CSS로 다시 출력(stringify)
```

이 구조 때문에 PostCSS는 단순히 “CSS 문법 하나”가 아니라, **CSS 빌드 파이프라인의 중간 엔진**처럼 동작합니다. ([PostCSS][2])

# 🤔 2. Sass와 무엇이 다른가?

이 부분이 가장 중요합니다.

## Sass

Sass는 **자체 문법/기능**이 있습니다.
예를 들면 변수, 믹스인, 중첩, 함수 같은 기능을 제공하고, Sass 코드를 CSS로 컴파일합니다.

## PostCSS

PostCSS는 기본적으로 “변환 엔진”입니다.
**그 자체가 변수나 믹스인을 제공하는 것이 아니라**, 그런 기능을 수행하는 **플러그인**을 연결해서 사용합니다.

예를 들어:

* 자동 vendor prefix 추가 → `Autoprefixer`
* Sass 비슷한 변수 → `postcss-simple-vars`
* 중첩 문법 → `postcss-nested`
* 최신 CSS 문법 변환 → `postcss-preset-env`
* 압축/최적화 → `cssnano`

공식 플러그인 디렉터리 역시 PostCSS의 핵심 가치가 “수백 개의 플러그인을 조합해 CSS를 변환하는 것”임을 보여줍니다. ([PostCSS][3])

즉, 아주 거칠게 비유하면:

> **Sass = 기능이 정해진 언어**
> **PostCSS = 기능을 조립하는 플랫폼**

입니다. ([PostCSS][2])

# ⚙️ 3. PostCSS의 핵심 철학

## “작은 플러그인들을 조합해서 원하는 CSS 파이프라인을 만든다”

PostCSS의 진짜 매력은 **모듈성**입니다.
하나의 거대한 도구가 모든 것을 처리하는 게 아니라, 필요한 기능만 골라 조합합니다.

예를 들면 이런 식입니다.

```js
module.exports = {
  plugins: [
    require('postcss-import'),
    require('postcss-nested'),
    require('autoprefixer'),
  ]
}
```

이 구성은 대략 다음 의미를 가집니다.

1. `@import`를 먼저 풀고
2. 중첩 문법을 일반 CSS로 변환하고
3. 마지막에 브라우저 호환성용 prefix를 붙인다

즉, **플러그인 순서 자체가 빌드 로직**이 됩니다. 공식 README의 예제도 `postcss([...plugins]).process(...)` 형태로 여러 플러그인을 연결해 처리하는 방식을 보여줍니다. ([GitHub][4])

# 🧠 4. PostCSS 내부 동작 원리

## AST 기반 변환이란 무엇인가?

PostCSS를 깊이 이해하려면 AST를 이해해야 합니다.

CSS를 사람이 볼 때는 그냥 문자열입니다.

```css
.button {
  display: flex;
}
```

그런데 PostCSS는 이것을 그냥 문자열 치환으로 다루지 않습니다.
파싱해서 구조화합니다.

예를 들면 개념적으로는 이런 트리입니다.

```text
Root
 └── Rule (.button)
      ├── Declaration (display: flex)
```

이렇게 AST가 만들어지면 플러그인은 다음 같은 작업을 할 수 있습니다.

* 특정 selector 찾기
* 특정 property 찾기
* declaration 추가/삭제/수정
* 새로운 rule 삽입
* at-rule(`@media`, `@supports`) 변형

공식 플러그인 작성 가이드도 대부분의 플러그인은 “무언가를 찾고(find), 그것을 변경(change)”하는 두 단계로 동작하며, PostCSS는 이를 위해 CSS를 노드 트리(AST)로 파싱한다고 설명합니다. ([PostCSS][5])

이게 왜 중요하냐면,
단순 정규식 기반 문자열 치환보다 **훨씬 안전하고 구조적**이기 때문입니다.
즉, “텍스트를 바꾸는 것”이 아니라 “CSS 구문 구조를 바꾸는 것”입니다. ([PostCSS][2])

# 🔌 5. 대표적인 PostCSS 플러그인들

## 5.1 Autoprefixer 🚗

가장 유명한 PostCSS 플러그인입니다.

역할은 아주 단순합니다.

```css
::placeholder {
  color: gray;
}
```

같은 CSS를 브라우저 호환성 데이터에 맞춰 적절한 vendor prefix가 붙은 결과로 변환합니다. Autoprefixer 공식 설명은 Can I Use 데이터를 바탕으로 CSS 규칙에 vendor prefix를 추가한다고 안내합니다. ([GitHub][6])

즉, 예전처럼 개발자가 직접:

```css
-webkit-...
-ms-...
```

를 손으로 쓰지 않게 도와주는 도구입니다. ([GitHub][6])

---

## 5.2 postcss-preset-env 🌍

아직 브라우저 지원이 완전하지 않은 최신 CSS 기능들을, 현재 브라우저 환경에서 동작 가능한 형태로 바꿔주는 계열의 도구입니다. PostCSS 공식 사이트는 `postcss-preset-env`를 통해 future CSS syntax를 사용할 수 있다고 소개합니다. ([PostCSS][7])

즉, 개발자는 더 현대적인 CSS 문법으로 작성하고, 빌드 시점에 호환성을 확보할 수 있습니다.

---

## 5.3 postcss-nested 🪆

Sass와 비슷한 중첩 문법을 일반 CSS로 풀어줍니다. 공식 저장소 설명도 Sass에 가까운 nested rule unwrapping 용도라고 밝히고 있습니다. ([GitHub][8])

예:

```css
.card {
  .title {
    font-size: 20px;
  }
}
```

를 표준 CSS 형태로 펼쳐줍니다.

---

## 5.4 postcss-simple-vars 💡

Sass 유사 변수 기능을 추가하는 플러그인입니다. 즉, PostCSS 자체가 변수를 제공하는 게 아니라, 이런 플러그인을 통해 그 기능을 얻는 구조입니다. ([GitHub][9])

---

## 5.5 cssnano 📦

배포용 CSS를 압축하고 최적화하는 데 자주 사용되는 PostCSS 생태계 도구입니다. 공식 플러그인 분류에서도 최적화(optimizations) 계열 플러그인이 중요한 축으로 소개됩니다. ([PostCSS][3])

---

# 🏗️ 6. PostCSS는 어디에서 사용되는가?

사실 많은 개발자가 **PostCSS를 직접 의식하지 않아도 이미 쓰고 있는 경우가 많습니다.**

대표적인 예가 다음입니다.

* Tailwind CSS
* Next.js의 CSS 처리
* 일부 Vite/Webpack 기반 빌드 파이프라인
* CSS Modules + Autoprefixer 구성
* Stylelint와 함께 쓰는 분석/검사 흐름

PostCSS 공식 README는 Autoprefixer와 Stylelint 계열이 대표적인 PostCSS 플러그인이라고 소개하고 있고, Tailwind 공식 문서도 PostCSS 플러그인 방식 설치를 명시적으로 안내합니다. Next.js 공식 가이드 역시 PostCSS 기반으로 Autoprefixer와 최신 CSS 처리 흐름을 설명합니다. ([GitHub][1])

# 🌪️ 7. Tailwind와 PostCSS의 관계

이 부분은 실무에서 아주 자주 헷갈립니다.

많은 분들이 Tailwind를 “CSS 프레임워크”로만 보는데,
빌드 관점에서는 **Tailwind도 PostCSS 플러그인 방식으로 동작할 수 있습니다.**

Tailwind 공식 문서는 PostCSS 방식 설치 시 `@tailwindcss/postcss`와 `postcss`를 설치하고, `postcss.config`에 해당 플러그인을 등록하도록 안내합니다. ([Tailwind CSS][10])

예를 들면 설정은 이런 느낌입니다.

```js
const config = {
  plugins: {
    "@tailwindcss/postcss": {},
  },
};

export default config;
```

즉, Tailwind는 단순한 CSS 파일이 아니라,
빌드 타임에 클래스 유틸리티를 생성하는 도구이며, 이 과정에서 PostCSS 생태계와 긴밀하게 연결됩니다. ([Tailwind CSS][10])

다만 최신 Tailwind 문서에서는 환경에 따라 Vite 전용 플러그인 같은 다른 권장 경로도 함께 제시하고 있으므로, “모든 프로젝트에서 무조건 PostCSS만이 정답”은 아닙니다. 프레임워크별 설치 가이드를 따르는 것이 안전합니다. ([Tailwind CSS][11])

# 🆚 8. PostCSS vs Sass

## 둘은 경쟁자라기보다 계층이 다릅니다

이 비교를 정확히 해야 헷갈리지 않습니다.

## Sass는

* 언어 기능을 제공하고
* Sass 코드를 CSS로 컴파일합니다

## PostCSS는

* CSS 또는 CSS 유사 문법을 파싱하고
* 플러그인으로 변환합니다

흥미로운 점은 PostCSS가 **커스텀 syntax**도 지원한다는 것입니다. 공식 문서는 SCSS 같은 커스텀 문법도 `parse`와 `stringify`를 제공하는 syntax 객체를 통해 다룰 수 있다고 설명합니다. 즉, 어떤 경우에는 SCSS 소스에 PostCSS 플러그인을 적용하는 것도 가능합니다. ([PostCSS][12])

그래서 실제 실무에서는:

* Sass만 사용
* PostCSS만 사용
* Sass + PostCSS 함께 사용

이 모두 가능합니다.
예를 들어 `SCSS → PostCSS(autoprefixer, cssnano) → 최종 CSS` 같은 파이프라인도 충분히 자연스럽습니다. ([PostCSS][12])

# 🧰 9. 실무 설정 파일은 어떻게 생기나?

가장 많이 보는 파일은 보통 이것입니다.

```js
// postcss.config.js
module.exports = {
  plugins: {
    autoprefixer: {},
  },
};
```

또는 ESM 환경이면:

```js
// postcss.config.mjs
const config = {
  plugins: {
    "@tailwindcss/postcss": {},
    autoprefixer: {},
  },
};

export default config;
```

실제 설정 문법은 빌드 도구와 패키지 버전에 따라 달라질 수 있지만, 핵심 개념은 동일합니다.

> **“어떤 플러그인들을 어떤 순서로 적용할 것인가?”**

입니다. Tailwind와 Next.js 공식 가이드 모두 PostCSS 구성 파일을 통해 플러그인을 연결하는 패턴을 안내합니다. ([Tailwind CSS][13])

# 🔍 10. PostCSS는 전처리기인가? 후처리기인가?

역사적으로는 PostCSS가 “후처리기(post-processor)”처럼 소개된 적이 많았습니다.
예를 들어 Autoprefixer처럼 “이미 작성된 CSS를 후처리”하는 느낌이 강했기 때문입니다.

그런데 지금은 그보다 훨씬 넓습니다.

* 최신 CSS 문법 변환
* 변수/중첩 같은 전처리기 유사 기능
* linting
* 최적화
* custom syntax 처리

즉, 오늘날의 PostCSS는 단순 후처리기를 넘어
**CSS 변환 파이프라인 전반을 담당하는 범용 엔진**이라고 보는 편이 더 정확합니다. 공식 문서도 linting, variables, mixins, transpile, inline images 등 매우 넓은 활용 범위를 직접 언급합니다. ([GitHub][1])

# 🧬 11. PostCSS 플러그인은 어떻게 동작하는가?

공식 플러그인 작성 가이드는 PostCSS 플러그인이 AST 노드를 방문하면서 특정 패턴을 찾고 변형하는 흐름을 설명합니다. 예를 들어 특정 declaration을 찾거나, 특정 at-rule을 처리하거나, 새로운 rule을 삽입할 수 있습니다. ([PostCSS][5])

개념적으로는 이런 식입니다.

```js
module.exports = () => {
  return {
    postcssPlugin: 'my-plugin',
    Declaration(decl) {
      if (decl.prop === 'color' && decl.value === 'red') {
        decl.value = 'blue';
      }
    }
  };
};

module.exports.postcss = true;
```

이 코드는 “모든 선언문 중 `color: red`를 찾아 `blue`로 바꾼다”는 식의 동작을 합니다.

여기서 중요한 것은, 플러그인이 문자열 전체를 무식하게 치환하는 것이 아니라
**선언(Declaration), 규칙(Rule), at-rule 같은 AST 노드 수준에서 작동**한다는 점입니다. 그래서 훨씬 안전하고 정교한 변환이 가능합니다. ([PostCSS][5])

# 🧱 12. PostCSS AST의 주요 노드들

플러그인 개발 관점에서 자주 만나는 노드는 대략 다음과 같습니다.

## Root

CSS 전체 문서의 루트입니다.

## Rule

일반 선택자 규칙입니다.

```css
.button { ... }
```

같은 블록이 여기에 해당합니다.

## Declaration

속성 선언입니다.

```css
color: red;
```

## AtRule

`@media`, `@supports`, `@import` 같은 규칙입니다.

공식 문서의 플러그인 설명 흐름도 이런 AST 노드를 중심으로 구성되어 있습니다. ([PostCSS][5])

즉, PostCSS를 깊게 이해한다는 것은 결국:

> “CSS를 문자열이 아니라 트리로 바라보는 사고방식”

을 익히는 것입니다. 🌳

# 🚨 13. 플러그인 순서가 중요한 이유

PostCSS에서 플러그인 순서는 정말 중요합니다.

예를 들어:

1. `postcss-import`
2. `postcss-nested`
3. `autoprefixer`
4. `cssnano`

이 순서는 꽤 자연스럽습니다.

왜냐하면:

* 먼저 import를 풀고
* 그 다음 중첩을 일반 CSS로 바꾸고
* 그 결과물에 prefix를 붙이고
* 마지막에 압축하는 것이 논리적이기 때문입니다

반대로 압축을 너무 먼저 하거나, 아직 풀리지 않은 문법에 prefix 작업을 먼저 걸면 원하는 결과가 안 나올 수 있습니다. PostCSS가 플러그인 체인 방식으로 동작한다는 공식 예제 구조 자체가 이 순서 의존성을 보여줍니다. ([GitHub][4])

# 🪄 14. Browserslist와 Autoprefixer의 관계

실무에서 Autoprefixer를 이해할 때 꼭 알아야 하는 것이 **브라우저 타깃 설정**입니다.

Autoprefixer는 Can I Use 데이터에 기반해 prefix를 붙이는데, 결국 “어느 브라우저까지 지원할 것인가”라는 기준이 있어야 합니다. 공식 설명도 Can I Use 기반 동작을 명시합니다. ([GitHub][6])

즉, PostCSS + Autoprefixer의 결과는 프로젝트의 브라우저 지원 정책에 따라 달라질 수 있습니다.

그래서 같은 CSS라도 어떤 프로젝트는 prefix가 더 많이 붙고, 어떤 프로젝트는 거의 안 붙을 수 있습니다.

---

# 🧭 15. Vite, Webpack, Next.js에서의 PostCSS

현대 프론트엔드 도구들은 대개 PostCSS와 쉽게 연결됩니다.

## Vite

CSS 처리 과정에서 PostCSS 설정 파일을 읽어 플러그인을 적용할 수 있습니다. Tailwind의 과거/일부 가이드도 Vite와 PostCSS 조합을 안내했습니다. ([Tailwind CSS][14])

## Next.js

공식 가이드는 PostCSS를 사용해 Autoprefixer와 최신 CSS 기능 처리 흐름을 설명합니다. ([Next.js][15])

## Tailwind 최신 가이드

최신 Tailwind 문서는 환경에 따라 Vite 플러그인 방식 또는 PostCSS 플러그인 방식을 각각 안내하므로, 최신 문서 기준으로 프로젝트별 권장 설치 방식을 선택해야 합니다. ([Tailwind CSS][11])

즉, 오늘날 PostCSS는 “직접 호출하는 라이브러리”이기도 하지만, 더 자주 보이는 모습은:

> **빌드 도구 뒤에서 조용히 동작하는 CSS 파이프라인 엔진**

입니다. ⚙️

# 🧑‍💻 16. 직접 JS API로 사용할 수도 있다

공식 README는 Node.js 코드에서 `postcss([...]).process(css, { from, to })` 형태로 직접 처리하는 예시를 제공합니다. ([GitHub][4])

개념적으로는 이런 형태입니다.

```js
const postcss = require('postcss');
const autoprefixer = require('autoprefixer');
const postcssNested = require('postcss-nested');

postcss([autoprefixer, postcssNested])
  .process(css, { from: 'src/app.css', to: 'dest/app.css' })
  .then(result => {
    console.log(result.css);
  });
```

이 방식은 빌드 도구 없이도 PostCSS를 라이브러리처럼 활용할 수 있다는 뜻입니다.
예를 들어 자체 빌드 스크립트, 문서 생성 파이프라인, 디자인 토큰 변환 도구 등에도 응용할 수 있습니다. ([GitHub][4])

# 🧯 17. 소스맵(source map)도 중요한 이유

PostCSS는 변환 결과뿐 아니라 소스맵도 함께 다룰 수 있습니다. 공식 예제 역시 `result.map`을 생성 파일과 함께 기록하는 흐름을 보여줍니다. ([GitHub][4])

왜 중요하냐면:

개발자 도구에서 최종 CSS를 볼 때, 실제로는 PostCSS를 거치며 변환된 결과물이 보이기 쉽습니다.
이때 소스맵이 있으면 브라우저가 “원본 어디서 왔는지”를 추적해 줍니다.

즉, 디버깅할 때:

* 내가 작성한 원본 CSS/SCSS
* 변환된 최종 CSS

사이의 연결 고리가 됩니다. 🔍

# 🧨 18. PostCSS를 사용할 때 자주 하는 오해

## 오해 1. “PostCSS = Autoprefixer”

아닙니다. Autoprefixer는 **PostCSS 플러그인 중 하나**입니다. PostCSS 전체와 동일하지 않습니다. ([GitHub][1])

## 오해 2. “PostCSS = Sass 대체재”

부분적으로 겹치는 영역은 있지만 완전히 같은 개념은 아닙니다. Sass는 언어이고, PostCSS는 플러그인 기반 변환 플랫폼입니다. ([PostCSS][2])

## 오해 3. “PostCSS는 브라우저에서 돌아간다”

아닙니다. 보통은 **빌드 단계(Node.js 환경)** 에서 실행됩니다. 브라우저 런타임에서 CSS를 바꾸는 도구가 아니라, 배포 전에 CSS를 준비하는 도구입니다. 공식 예시도 Node.js 처리 흐름입니다. ([GitHub][4])

## 오해 4. “플러그인은 아무 순서나 상관없다”

아닙니다. 순서에 따라 결과가 달라질 수 있습니다. PostCSS는 플러그인 체인 구조이기 때문입니다. ([GitHub][4])

# 🏆 19. 언제 PostCSS를 적극적으로 써야 하는가?

다음 상황이면 아주 강력합니다.

* 브라우저 호환성 관리가 필요할 때
* 최신 CSS 문법을 안전하게 쓰고 싶을 때
* Tailwind 같은 도구와 함께 CSS 파이프라인을 구성할 때
* CSS 최적화/압축까지 자동화하고 싶을 때
* 팀 차원에서 일관된 빌드 규칙을 만들고 싶을 때

반대로 아주 단순한 정적 페이지라면 PostCSS의 존재를 직접 느끼지 못할 수도 있습니다.
하지만 규모가 커질수록 “사람이 손으로 CSS를 맞추는 일”을 자동화하는 가치가 커집니다. ([GitHub][1])

> **PostCSS는 CSS를 AST로 파싱한 뒤, 플러그인으로 분석·변환·최적화하는 JavaScript 기반 CSS 변환 플랫폼입니다.** ([PostCSS][2])

# ✨ 최종 핵심 요약

PostCSS의 본질은 “CSS를 더 똑똑하게 다루기 위한 중간 엔진”입니다.
Sass처럼 하나의 문법을 제공하는 언어라기보다, **플러그인들을 조합해서 나만의 CSS 처리 파이프라인을 설계하는 플랫폼**입니다. 공식 문서 기준으로도 PostCSS는 단순 prefix 도구가 아니라, future syntax, linting, custom syntax, optimization 등 매우 넓은 생태계를 가진 도구입니다. ([GitHub][1])

그래서 실무에서는 이렇게 이해하시면 가장 정확합니다.

* **Sass**는 “CSS를 더 편하게 쓰는 언어”
* **PostCSS**는 “CSS를 더 똑똑하게 변환하는 엔진”
* **Autoprefixer / Tailwind / cssnano** 등은 “그 엔진 위에서 돌아가는 플러그인들”

입니다. 🚀 ([GitHub][6])
