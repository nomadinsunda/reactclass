# React.Suspense 완전 정복 가이드 ⏳

*“로딩 스피너 지옥에서 구해주는 선언적 로딩 처리기”*

---

## 0. 한 줄 요약부터 🎯

> **`React.Suspense`는 “일부 UI가 아직 준비되지 않았을 때, 그 부분을 잠깐 다른 UI(로딩 등)로 대체해 주는 경계(boundary)”입니다.**
>
> * 자식 컴포넌트가 **비동기 준비 중**일 때 → `fallback`을 보여줌
> * 준비가 끝나면 → **자동으로 실제 UI로 스왑**

즉,
`로딩 상태 관리 useState + if (loading) ...` 를 **컴포넌트 바깥 “레이아웃 레벨”에서 깔끔하게 선언**하는 개념입니다.

---

## 1. 왜 Suspense가 나왔을까? 🤯

전통적인 React 로딩 처리:

```jsx
function UserProfile() {
  const [user, setUser] = useState(null)
  const [loading, setLoading] = useState(true)

  useEffect(() => {
    fetch('/api/user')
      .then(res => res.json())
      .then(data => {
        setUser(data)
        setLoading(false)
      })
  }, [])

  if (loading) {
    return <Spinner />
  }

  return <ProfileView user={user} />
}
```

문제점들:

1. **로딩 여부를 매번 컴포넌트마다 관리**해야 함
2. 로딩 UI가 여기저기 흩어져 있음 (`if (loading) return ...`)
3. 페이지 전체가 아닌 “일부분만” 로딩 상태로 처리하기가 점점 더 복잡

→ React 팀의 생각:
“**로딩 같은 건 ‘레이아웃 레벨’에서 한 번에 선언하면 안 될까?**”
→ 그래서 나온 것이 **`<Suspense>`** 입니다.

---

## 2. 기본 문법: React.lazy + Suspense 🔌

먼저 가장 유명한 조합인 **코드 스플리팅 + Suspense**부터 보겠습니다.

### 2-1. `React.lazy`로 지연 로딩 컴포넌트 만들기

```jsx
import React, { Suspense, lazy } from 'react'

// 번들을 쪼개고, 이 컴포넌트는 실제로 필요할 때 네트워크로 불러옴
const HeavyChart = lazy(() => import('./HeavyChart'))

export default function DashboardPage() {
  return (
    <main>
      <h1>Dashboard</h1>

      <Suspense fallback={<p>차트 로딩 중... ⏳</p>}>
        <HeavyChart />
      </Suspense>
    </main>
  )
}
```

여기서 일어나는 일:

* `DashboardPage` 렌더링 시 React는 `HeavyChart`를 **아직 다운로드하지 못했을 수 있음**
* `HeavyChart` 내부에서 **“나 준비 안 됐어!”** 라고 신호(실제로는 Promise throw)를 던지면
* 가장 가까운 `<Suspense>`가 그것을 **잡아서** `fallback`을 렌더링
* **번들 다운로드 + 컴포넌트 준비 완료** → `fallback` → 진짜 `<HeavyChart />`로 자동 교체

> ❗핵심: **로딩 상태를 useState로 직접 관리 안 해도**, Suspense boundary가 알아서 “기다렸다가 보여주기”를 수행

## 3. Suspense 내부에서 실제로 무슨 일이? 🧠

조금 더 깊게 들어가 보겠습니다. (교육용 설명)

### 3-1. 트리 구조 관점에서의 Suspense

```txt
<App>
 ├─ <Header />
 └─ <Suspense fallback={<Loading />}>
      └─ <HeavyChart />  // 아직 준비 안 됨
```

렌더링 흐름 (개념적 설명):

1. React가 `<HeavyChart />`를 렌더하려고 함
2. 아직 코드가 안 받아졌거나, 데이터가 안 왔다면
   → `HeavyChart`는 **Promise를 던짐** (React 내부 프로토콜)
3. React는

   * “아, 이 부분은 **지금은 못 그리는구나**”라고 판단
   * 위로 올라가면서 **가장 가까운 `<Suspense>`**를 찾음
4. 해당 Suspense에 대해:

   * “이 boundary는 아직 **pending** 상태다”
   * → 대신 `fallback`을 렌더 (`<Loading />`)
5. 나중에 Promise가 resolve되면:

   * “이 boundary 다시 렌더!” → 이번에는 `<HeavyChart />`가 정상 렌더 → `fallback` 제거

이 방식 덕분에, React는 **렌더링 과정에서 비동기를 자연스럽게 끼워 넣을 수 있게** 됩니다.
이걸 활용해서 **Concurrent Rendering**, **데이터 기반 Suspense** 같은 기능들이 구현됩니다.

## 4. Suspense는 어디에 쓰는가? (두 가지 대표 용도) 🧰

### 4-1. (1) 코드 스플리팅 / Lazy Loading

이미 본 것처럼:

* 페이지 일부(특히 무거운 컴포넌트)를 **나중에 네트워크로 불러오고**
* 그동안 **Skeleton / 스피너 / Placeholder**를 보여주는 용도

```jsx
const UserSettings = lazy(() => import('./UserSettings'))

function SettingsPage() {
  return (
    <Suspense fallback={<SettingsSkeleton />}>
      <UserSettings />
    </Suspense>
  )
}
```

**장점**:

* 번들 크기 감소 → 초기 로딩 속도 향상 🚀
* 로딩 처리 로직이 깔끔하게 하나의 boundary로 모임

---

### 4-2. (2) 데이터 가져오기(Data Fetching)와 Suspense

React 18 이후, **데이터 로딩도 Suspense로 처리**하는 방향으로 계속 진화하고 있습니다.

* `React.lazy`는 “코드”를 늦게 가져오는 것
* 데이터 fetching에서는 “데이터”를 늦게 가져오는 것

핵심 아이디어는 **똑같습니다**:

> “준비 안 된 컴포넌트/데이터 → Promise 던짐 → Suspense가 잡고 fallback 렌더”

실전에서는 **React Query, Relay, Next.js, Remix** 같은 프레임워크/라이브러리가
Suspense와 연동되는 데이터 fetching API를 제공하는 방식으로 많이 사용됩니다.

예를 들어, 개념적인 pseudo 코드:

```jsx
function useUser() {
  const user = someSuspenseEnabledDataSource.read('/api/user')
  return user
}

function UserProfile() {
  const user = useUser()
  return <div>{user.name}</div>
}

export default function Page() {
  return (
    <Suspense fallback={<p>사용자 정보 불러오는 중... ⏳</p>}>
      <UserProfile />
    </Suspense>
  )
}
```

여기서 `someSuspenseEnabledDataSource.read`가 준비 안 된 상태면 Promise를 던지고,
`<Suspense>`가 fallback을 보여주는 구조입니다.

> ⚠️ 순수 React만으로 이걸 직접 구현하려면 “리소스 wrapper 패턴” 같은 걸 써야 해서 조금 복잡합니다.
> 실제 실무에서는 **Suspense 지원하는 라이브러리 / 프레임워크와 함께 사용하는 것이 일반적**입니다.

## 5. Suspense 사용 시 설계 포인트 🎨

### 5-1. 어디까지를 하나의 boundary로 묶을까?

두 가지 극단:

1. **페이지 전체를 하나의 Suspense로**

   ```jsx
   <Suspense fallback={<PageSpinner />}>
     <Page />
   </Suspense>
   ```

   * 장점: 구현이 단순
   * 단점: 작은 부분 하나 때문에 **페이지 전체가 로딩 화면**이 될 수 있음

2. **부분별로 여러 개의 Suspense로 쪼개기**

   ```jsx
   function Dashboard() {
     return (
       <>
         <Header />
         <div className="grid grid-cols-2 gap-4">
           <Suspense fallback={<CardSkeleton />}>
             <UserSummaryCard />
           </Suspense>

           <Suspense fallback={<CardSkeleton />}>
             <SalesChartCard />
           </Suspense>
         </div>
       </>
     )
   }
   ```

   * 장점: 한 카드가 늦게 로드되어도 다른 카드들은 **먼저 렌더** 가능 → **부분적 점진 로딩**
   * 단점: Suspense boundary가 많아질수록 설계 고민이 늘어남

> **실무 팁**:
>
> * “페이지 전체 스피너” 1개 + “중요한 큰 섹션” 정도에만 별도 Suspense를 두는 식으로 시작
> * 성능/UX 보고 점점 세분화

---

### 5-2. Nested Suspense (중첩)

```jsx
<Suspense fallback={<PageSkeleton />}>
  <Header />
  <main>
    <Suspense fallback={<SidebarSkeleton />}>
      <Sidebar />
    </Suspense>

    <Suspense fallback={<ContentSkeleton />}>
      <MainContent />
    </Suspense>
  </main>
</Suspense>
```

동작 개념:

* `MainContent`가 느림 → `ContentSkeleton`만 보여주고 나머지는 그대로
* 만약 최상위 fetch에서 큰 문제가 있다면 → `PageSkeleton`이 전체를 감쌀 수 있음

Suspense는 **가장 가까운 boundary**가 fallback을 책임지고,
위쪽 boundary는 더 **큰 레벨의 로딩 전략**을 담당합니다.

## 6. Suspense vs ErrorBoundary ⚖️

둘 다 “경계(boundary)”라는 점에서 자주 같이 이야기됩니다.

| 항목       | Suspense ⏳                    | ErrorBoundary 💥            |
| -------- | ----------------------------- | --------------------------- |
| 목적       | **“아직 준비 안 된 비동기 상태” 처리       | **렌더링 중 발생한 에러** 처리         |
| 트리거      | Promise throw (pending)       | Error throw                 |
| UI       | `fallback`로 로딩/placeholder 표시 | `fallback`로 에러 메시지/대체 UI 표시 |
| 주 사용 케이스 | 코드 스플리팅, 데이터 로딩               | 런타임 에러 캡처, 깨진 UI 영역 격리      |

실무에서는 보통 이렇게 같이 감쌉니다:

```jsx
<ErrorBoundary fallback={<ErrorScreen />}>
  <Suspense fallback={<LoadingScreen />}>
    <App />
  </Suspense>
</ErrorBoundary>
```

* 데이터/코드가 아직이면 → `LoadingScreen`
* 렌더링 중 예외 터지면 → `ErrorScreen`

## 7. Suspense와 Concurrent Features (useTransition 등) 🚦

React 18에서 Suspense는 **Concurrent Rendering 기능들과 같이 쓰면서 진가를 발휘**합니다.

### 7-1. `useTransition` + Suspense

예: 검색 결과 리스트를 Suspense로 감싸고, 입력 도중 “기존 UI 유지 + 새 결과는 뒤에서 준비” 패턴

```jsx
import { Suspense, useState, useTransition } from 'react'
import SearchResultList from './SearchResultList'

export default function SearchPage() {
  const [query, setQuery] = useState('')
  const [pendingQuery, setPendingQuery] = useState('')
  const [isPending, startTransition] = useTransition()

  const handleChange = (e) => {
    const value = e.target.value
    setQuery(value)               // 입력 값은 즉시 반영 (빠른 UI)
    startTransition(() => {
      setPendingQuery(value)      // 이 값 기준으로 비싼 작업/데이터 로딩
    })
  }

  return (
    <div>
      <input
        value={query}
        onChange={handleChange}
        placeholder="검색어를 입력하세요"
      />

      {isPending && <p>검색 중... 🔍</p>}

      <Suspense fallback={<p>결과 로딩 중... ⏳</p>}>
        <SearchResultList query={pendingQuery} />
      </Suspense>
    </div>
  )
}
```

개념:

* 입력 값은 바로바로 업데이트 (`query`) → 사용자는 지연 없이 타이핑 감지
* 실제로 무거운 검색/데이터 로딩은 `startTransition` 블록에서 수행 (`pendingQuery`)
* 그 과정에서 `SearchResultList`가 Suspense를 통해 로딩 UI로 대체

이렇게 하면 **“타이핑은 매끄럽고, 결과는 천천히 업데이트되는” UX**를 만들 수 있습니다.

## 8. 간단한 Vite + React (JS) 예제 📦

사용자분이 자주 쓰시는 **Vite + React (JS)** 기준으로 예시를 하나 정리해 보겠습니다.

### 8-1. lazy 컴포넌트

`src/features/Reports.jsx` (무거운 컴포넌트라고 가정)

```jsx
export default function Reports() {
  // 이 안에서 그래프 라이브러리, 큰 테이블 등 렌더한다고 가정
  return (
    <section className="p-4 border rounded">
      <h2 className="text-xl font-bold mb-2">Reports</h2>
      <p>여기에 아주 무거운 통계 그래프들이 그려진다고 상상해봅시다 📊</p>
    </section>
  )
}
```

### 8-2. Suspense로 감싸기

`src/App.jsx`

```jsx
import { Suspense, lazy } from 'react'

const Reports = lazy(() => import('./features/Reports'))

function ReportsSkeleton() {
  return (
    <section className="p-4 border rounded animate-pulse">
      <div className="h-6 w-32 bg-gray-300 mb-4" />
      <div className="h-4 w-full bg-gray-200 mb-2" />
      <div className="h-4 w-5/6 bg-gray-200" />
    </section>
  )
}

export default function App() {
  return (
    <main className="p-8 space-y-4">
      <h1 className="text-2xl font-bold mb-4">Dashboard ⏳ Suspense Demo</h1>

      <Suspense fallback={<ReportsSkeleton />}>
        <Reports />
      </Suspense>
    </main>
  )
}
```

여기서:

* 번들이 처음 로드될 때 `Reports`는 **별도 청크**로 나가 있음
* 사용자가 Dashboard로 들어오면

  * 처음에는 `ReportsSkeleton`이 보이고
  * JS 청크가 네트워크에서 받아지고 평가가 끝나면
  * 자동으로 `<Reports />`가 렌더됩니다.

별도의 `loading` state 관리 없음 👍

## 9. Suspense 사용할 때 자주 하는 오해/주의사항 😅

1. **“아무 비동기나 Suspense가 자동으로 처리해 주겠지?” → NO**

   * Suspense는 **React가 이해할 수 있는 방식으로 Promise를 던지는 코드**에만 동작
   * 그냥 `useEffect`에서 fetch 하고 state 세팅하는 패턴은 Suspense와 무관

2. **“에러도 Suspense가 처리해 주겠지?” → NO**

   * 에러는 **ErrorBoundary**가 담당
   * Suspense는 “로딩 중”을 처리

3. **“Suspense 하나만 크게 둘러치면 UX 끝!” → 애매**

   * 페이지 전체가 로딩 화면으로 바뀌면,
     사용자가 “내가 뭘 하고 있었지?” 하는 느낌이 들 수 있음
   * 적절히 잘라서 부분 Suspense boundary를 만드는 게 중요

4. **서버 렌더링(SSR)과의 상호작용**

   * React 18 이후 Server-Side Rendering / Streaming / Server Components와
     Suspense가 긴밀하게 연동되고 있어서,
     Next.js 13+ 같은 환경에서는 **서버 단계에서부터 Suspense가 개입**합니다.
   * 이때는 “서버에서 먼저 일부 HTML chunk를 보내고, 나중에 나머지를 스트리밍” 같은 패턴도 가능.

---

## 10. 정리 ✅

React.Suspense는 단순히 “로딩 스피너 달기 도와주는 컴포넌트”가 아니라:

* **렌더링 과정에 비동기를 자연스럽게 통합하기 위한 핵심 메커니즘**
* 코드 스플리팅, 데이터 로딩, 스트리밍 SSR, React 18 concurrent features의 **중심에 있는 개념**
* “로딩 상태”를 각 컴포넌트에서 관리하는 대신,
  **UI 레이아웃 레벨에서 선언적으로 설계**할 수 있게 해 줍니다.
