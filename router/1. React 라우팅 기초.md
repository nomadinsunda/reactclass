# React Routing

## SPA의 URL과 UI를 연결하는 클라이언트 사이드 라우팅

React 애플리케이션을 개발하다 보면 반드시 만나게 되는 개념이 **라우팅(Routing)**입니다.

일반적인 웹사이트에서는 URL이 변경되면 다른 페이지가 나타납니다.

```text
/             → Home
/about        → About
/products     → ProductList
/products/10  → ProductDetail
```

겉으로 보면 단순히 "URL에 따라 페이지를 보여주는 것"처럼 보입니다.

하지만 SPA(Single Page Application)에서는 전통적인 웹 애플리케이션과 라우팅 방식이 상당히 다릅니다.

React Router를 제대로 이해하려면 먼저 다음 질문에서 시작해야 합니다.

> 브라우저가 새로운 HTML 문서를 서버에서 받아오지 않는데, 어떻게 URL과 화면을 동시에 변경할 수 있을까?

이 문제를 해결하는 것이 **클라이언트 사이드 라우팅(Client-side Routing)**이며, React에서는 대표적으로 React Router를 사용합니다.

---

# 1. 라우팅이란?

라우팅은 간단히 말하면

> **현재 URL을 해석하여 그 URL에 대응하는 화면 또는 동작을 결정하는 과정**

입니다.

예를 들어 다음과 같은 규칙을 만들 수 있습니다.

```text
/             → Home
/about        → About
/products     → ProductList
/products/10  → ProductDetail
```

여기서 중요한 것은 **누가 URL을 해석하여 화면을 결정하느냐**입니다.

전통적인 웹 애플리케이션에서는 주로 서버가 담당했고, SPA에서는 상당 부분을 브라우저에서 실행되는 JavaScript 애플리케이션이 담당합니다.

---

# 2. MPA의 서버 사이드 라우팅

전통적인 MPA(Multi Page Application)에서는 URL이 변경되면 일반적으로 새로운 문서를 서버에 요청합니다.

예를 들어 사용자가 다음 링크를 클릭한다고 해보겠습니다.

```html
<a href="/about">About</a>
```

일반적인 흐름은 다음과 같습니다.

```text
사용자
  │
  │ /about 클릭
  ▼
Browser
  │
  │ GET /about
  ▼
Server
  │
  │ HTML 응답
  ▼
Browser
  │
  │ 새로운 Document 로드
  ▼
새로운 화면
```

즉,

```text
URL 변경
   ↓
HTTP 요청
   ↓
서버 라우팅
   ↓
새 HTML 응답
   ↓
Document 교체
   ↓
화면 갱신
```

이 방식에서는 서버가 URL을 해석하여 적절한 HTML 문서나 응답을 반환합니다.

따라서 라우팅의 중심이 **서버**에 있습니다.

---

# 3. SPA의 클라이언트 사이드 라우팅

React SPA에서는 초기 접속 시 일반적으로 서버에서 `index.html`을 받아오고, React 애플리케이션의 JavaScript 코드가 실행됩니다.

```text
Browser
   │
   │ GET /
   ▼
Server
   │
   │ index.html
   ▼
Browser
   │
   ├─ JavaScript 로딩
   │
   └─ React 실행
          │
          ▼
       React UI
```

그 이후 애플리케이션 내부에서 `/about`으로 이동한다고 해서 반드시 새로운 HTML 문서를 서버에서 받아올 필요는 없습니다.

대신 개념적으로 다음과 같이 동작합니다.

```text
현재 URL
   │
   ▼
React Router
   │
   │ URL과 Route 비교
   ▼
매칭된 Route
   │
   ▼
React Component
   │
   ▼
화면 렌더링
```

예를 들어:

```text
/             → <Home />
/about        → <About />
/products     → <ProductList />
```

따라서 SPA 라우팅의 핵심은

> **새로운 HTML 문서로 이동하는 대신 현재 URL에 대응하는 React 컴포넌트 트리를 렌더링하는 것**

입니다.

---

# 4. SPA에서는 어떻게 새로고침 없이 URL을 변경하는가?

여기서 중요한 문제가 하나 발생합니다.

브라우저 주소창의 URL은 변경하고 싶지만 새로운 HTML 문서를 서버에 요청하고 싶지는 않습니다.

이를 가능하게 해주는 브라우저 API가 **History API**입니다.

대표적으로 다음 API가 사용됩니다.

```js
history.pushState()
history.replaceState()
```

그리고 브라우저의 세션 히스토리 이동을 감지하는 데 다음 이벤트가 사용됩니다.

```js
popstate
```

예를 들어:

```js
history.pushState({}, '', '/about');
```

를 실행하면 주소창은

```text
https://example.com/
```

에서

```text
https://example.com/about
```

으로 변경될 수 있습니다.

하지만 이 동작 자체는 `/about` 문서를 서버에 요청하여 새로운 Document를 로드하지 않습니다.

즉,

```text
history.pushState()
        │
        ├── URL 변경
        ├── History Entry 추가
        │
        └── 새로운 Document 요청 없음
```

이 기능이 SPA 라우팅을 가능하게 만드는 브라우저의 핵심 기반 기술입니다.

---

# 5. pushState와 popstate는 구분해야 한다

여기서 자주 발생하는 오해가 있습니다.

```js
history.pushState(...)
```

를 호출한다고 해서 `popstate` 이벤트가 발생하는 것은 아닙니다.

`popstate`는 대표적으로 사용자가 브라우저의 **뒤로 가기 / 앞으로 가기**를 통해 세션 히스토리를 이동할 때 사용됩니다.

개념적으로:

```text
<Link> 클릭
     │
     ▼
React Router navigation
     │
     ├── History 변경
     │
     └── Router 상태 갱신
              │
              ▼
        새로운 Route 계산
              │
              ▼
        React 렌더링
```

반면 사용자가 브라우저의 뒤로 가기를 누르면:

```text
뒤로 가기
    │
    ▼
Browser History 이동
    │
    ▼
popstate
    │
    ▼
Router가 위치 변경 인식
    │
    ▼
Route 다시 계산
    │
    ▼
React 렌더링
```

따라서 History API는 React Router가 동작할 수 있게 해주는 **브라우저 수준의 기반 기술**이라고 이해하면 좋습니다.

---

# 6. React Router의 역할

React Router의 핵심 역할은 크게 다음과 같이 볼 수 있습니다.

```text
URL
 │
 ▼
Location
 │
 ▼
Route Matching
 │
 ▼
Matched Route
 │
 ▼
React Element
 │
 ▼
React Rendering
```

즉,

> **React Router는 현재 URL과 Route 설정을 연결하여 어떤 React UI를 렌더링할지 결정하는 라우팅 시스템이다.**

라고 정의할 수 있습니다.

단순히 URL을 변경하는 라이브러리라고 이해하면 부족합니다.

React Router는 크게 다음 문제를 해결합니다.

* URL 관리
* Route matching
* 화면 선택
* 중첩 UI
* 동적 URL 파라미터
* 브라우저 History 연동
* 프로그램 방식의 navigation
* URL search parameter 관리

---

# 7. BrowserRouter

가장 기본적인 선언형 라우팅에서는 애플리케이션 최상위에 `BrowserRouter`를 배치할 수 있습니다.

```jsx
import { BrowserRouter } from "react-router-dom";

<BrowserRouter>
  <App />
</BrowserRouter>
```

`BrowserRouter`는 브라우저 History API를 기반으로 현재 location을 관리하고 하위 컴포넌트가 Router 기능을 사용할 수 있도록 합니다.

중요한 점이 있습니다.

> **BrowserRouter 자체가 서버에게 "모든 URL에 index.html을 반환하라"고 설정하는 것은 아닙니다.**

예를 들어 사용자가 주소창에 직접 다음 URL을 입력하면:

```text
https://example.com/products/10
```

브라우저는 서버에 실제로 요청합니다.

```http
GET /products/10
```

따라서 SPA를 배포할 때는 서버가 해당 요청에 대해 SPA의 진입 문서인 `index.html`을 반환하도록 fallback 설정을 해주는 경우가 많습니다.

개념적으로:

```text
GET /products/10
        │
        ▼
      Server
        │
        ▼
   index.html
        │
        ▼
   React 실행
        │
        ▼
React Router
        │
        ▼
<ProductDetail />
```

이 부분은 **React Router 설정과 웹 서버 설정을 구분해서 이해해야 합니다.**

# 8. Routes와 Route

기본적인 Route 설정은 다음과 같이 작성할 수 있습니다.

```jsx
import { Routes, Route } from "react-router-dom";

<Routes>
  <Route path="/" element={<Home />} />
  <Route path="/about" element={<About />} />
</Routes>
```

여기서 `Route`는 URL 패턴과 렌더링할 React element를 연결합니다.

```text
path="/"       → <Home />
path="/about"  → <About />
```

따라서:

```text
현재 URL
   │
   ▼
<Routes>
   │
   ├── /
   ├── /about      ← match
   └── /products
          │
          ▼
       <About />
```

와 같은 방식으로 이해할 수 있습니다.

---

# 9. Link

일반 HTML 링크는 다음과 같습니다.

```html
<a href="/about">About</a>
```

이 링크를 일반적인 방식으로 탐색하면 브라우저는 `/about`에 대한 새로운 문서 탐색을 수행합니다.

SPA 내부 navigation에서는 React Router의 `Link`를 사용할 수 있습니다.

```jsx
import { Link } from "react-router-dom";

<Link to="/about">About</Link>
```

React Router가 처리할 수 있는 내부 navigation이라면 새로운 HTML Document를 다시 로드하지 않고 클라이언트 라우팅을 수행할 수 있습니다.

```text
<Link> 클릭
    │
    ▼
React Router
    │
    ▼
History / Location 변경
    │
    ▼
Route Matching
    │
    ▼
React Rendering
```

다만 "서버 요청이 전혀 발생하지 않는다"라고 표현하는 것은 정확하지 않습니다.

라우트 이동 과정에서 API 요청이나 lazy-loaded JavaScript chunk 요청 등이 발생할 수 있기 때문입니다.

정확한 표현은:

> **새로운 HTML Document를 가져오기 위한 전체 페이지 navigation이 발생하지 않는다.**

입니다.

# 10. useNavigate

사용자의 특정 동작이나 애플리케이션 로직에 따라 프로그램 방식으로 이동해야 하는 경우 `useNavigate()`를 사용할 수 있습니다.

```jsx
import { useNavigate } from "react-router-dom";

function Login() {
  const navigate = useNavigate();

  const handleLogin = () => {
    // 로그인 처리
    navigate("/mypage");
  };

  return (
    <button onClick={handleLogin}>
      Login
    </button>
  );
}
```

개념적으로:

```text
로그인 성공
    │
    ▼
navigate("/mypage")
    │
    ▼
Location 변경
    │
    ▼
Route Matching
    │
    ▼
<MyPage />
```

입니다.

# 11. 중첩 라우팅

실제 애플리케이션의 URL은 계층 구조를 갖는 경우가 많습니다.

```text
/products
/products/10
/products/10/reviews
```

React Router에서는 이러한 구조를 중첩 Route로 표현할 수 있습니다.

```jsx
<Routes>
  <Route path="/products" element={<ProductsLayout />}>
    <Route index element={<ProductList />} />
    <Route path=":id" element={<ProductDetail />} />
    <Route path=":id/reviews" element={<ProductReviews />} />
  </Route>
</Routes>
```

부모 컴포넌트에서는 `Outlet`을 사용합니다.

```jsx
import { Outlet } from "react-router-dom";

function ProductsLayout() {
  return (
    <div>
      <h1>상품 페이지</h1>
      <Outlet />
    </div>
  );
}
```

`Outlet`은 현재 매칭된 자식 Route의 element가 렌더링되는 위치입니다.

```text
ProductsLayout
│
├── <h1>상품 페이지</h1>
│
└── <Outlet />
       │
       └── ProductDetail
```

따라서 중첩 라우팅은 **URL 구조와 UI 계층 구조를 자연스럽게 연결**할 수 있게 해줍니다.

# 12. 동적 라우팅

URL의 일부를 동적인 값으로 사용할 수도 있습니다.

예를 들어:

```text
/products/10
/products/20
/products/100
```

이 URL들을 모두 별도의 Route로 작성할 필요는 없습니다.

```jsx
<Route
  path="/products/:id"
  element={<ProductDetail />}
/>
```

`:id`는 동적 URL segment입니다.

컴포넌트에서는 `useParams()`를 사용하여 값을 가져올 수 있습니다.

```jsx
import { useParams } from "react-router-dom";

function ProductDetail() {
  const { id } = useParams();

  return <div>Product ID: {id}</div>;
}
```

예를 들어:

```text
URL
/products/10
       │
       ▼
path="/products/:id"
                  │
                  ▼
              id = "10"
```

처럼 매칭됩니다.

# 13. 인증이 필요한 Route

SPA에서는 인증 상태에 따라 특정 화면의 접근을 제한하는 패턴을 사용할 수 있습니다.

예를 들어:

```jsx
function ProtectedRoute({ children }) {
  const isAuthenticated = useAuth();

  if (!isAuthenticated) {
    return <Navigate to="/login" replace />;
  }

  return children;
}
```

사용:

```jsx
<Route
  path="/mypage"
  element={
    <ProtectedRoute>
      <MyPage />
    </ProtectedRoute>
  }
/>
```

흐름은 다음과 같습니다.

```text
/mypage 접근
     │
     ▼
인증 상태 확인
     │
 ┌───┴────┐
 │        │
인증됨   인증 안 됨
 │        │
 ▼        ▼
MyPage   /login
```

이를 흔히 **Protected Route 또는 Route Guard 패턴**이라고 부릅니다.

다만 React Router가 `RouteGuard`라는 별도의 보안 기능을 제공하는 것은 아닙니다.

또한 클라이언트의 Route 접근을 막는 것만으로 서버의 데이터가 보호되는 것은 아닙니다.

> **실제 API와 데이터에 대한 권한 검사는 반드시 서버에서도 수행해야 합니다.**

# 14. 코드 스플리팅과 Lazy Loading

페이지별 JavaScript 코드를 처음부터 전부 다운로드할 필요가 없는 경우 React의 `lazy()`와 `Suspense`를 사용할 수 있습니다.

```jsx
import { lazy, Suspense } from "react";

const About = lazy(() => import("./pages/About"));

<Route
  path="/about"
  element={
    <Suspense fallback={<Loading />}>
      <About />
    </Suspense>
  }
/>
```

이 경우 `About`에 필요한 JavaScript chunk를 필요할 때 로드할 수 있습니다.

개념적으로:

```text
초기 접속
   │
   ├── Home 관련 JS
   │
   └── About JS는 아직 로드하지 않음

/about 이동
   │
   ▼
About chunk 요청
   │
   ▼
About module 로딩
   │
   ▼
<About /> 렌더링
```

이를 통해 초기 JavaScript bundle의 크기를 줄이는 데 도움을 줄 수 있습니다.

# 15. 404 처리

어떤 Route에도 매칭되지 않는 URL을 처리하려면 wildcard route를 사용할 수 있습니다.

```jsx
<Route path="*" element={<NotFound />} />
```

예를 들어:

```text
/about        → About
/products     → Products
/abcdef       → *
                 │
                 ▼
             NotFound
```

# 16. 전체 라우팅 구조

지금까지의 내용을 하나로 합치면 다음과 같은 구조를 만들 수 있습니다.

```jsx
<BrowserRouter>
  <Routes>
    <Route path="/" element={<Home />} />

    <Route path="/products" element={<ProductsLayout />}>
      <Route index element={<ProductList />} />
      <Route path=":id" element={<ProductDetail />} />
      <Route
        path=":id/reviews"
        element={<ProductReviews />}
      />
    </Route>

    <Route path="/about" element={<About />} />

    <Route
      path="/mypage"
      element={
        <ProtectedRoute>
          <MyPage />
        </ProtectedRoute>
      }
    />

    <Route path="*" element={<NotFound />} />
  </Routes>
</BrowserRouter>
```

# 17. React Router의 전체 동작 흐름

React Router의 핵심 흐름을 하나의 그림으로 정리하면 다음과 같습니다.

```text
사용자
 │
 │ <Link to="/products/10">
 ▼
React Router
 │
 │ navigation 처리
 ▼
Browser History / Location
 │
 │
 ▼
URL
/products/10
 │
 ▼
Route Matching
 │
 │ "/products/:id"
 ▼
Params
id = "10"
 │
 ▼
Matched React Element
<ProductDetail />
 │
 ▼
React Render
 │
 ▼
화면 변경
```

이 과정에서 새로운 HTML Document를 다시 받아오는 전체 페이지 navigation은 발생하지 않습니다.

---

# 18. 새로고침하면 왜 서버 설정이 필요한가?

SPA 라우팅에서 반드시 이해해야 하는 중요한 부분입니다.

애플리케이션 내부에서:

```text
/products/10
```

으로 이동한 경우에는 React Router가 처리할 수 있습니다.

하지만 사용자가 해당 주소에서 브라우저를 새로고침하면 상황이 달라집니다.

브라우저는 서버에 직접 요청합니다.

```http
GET /products/10
```

서버가 `/products/10`이라는 실제 파일이나 서버 Route를 찾으려고 한다면 404가 발생할 수 있습니다.

따라서 SPA 배포 환경에서는 일반적으로:

```text
GET /products/10
        │
        ▼
      Server
        │
        ▼
   index.html 반환
        │
        ▼
   React 실행
        │
        ▼
React Router가
/products/10 해석
        │
        ▼
<ProductDetail />
```

과 같은 fallback 설정이 필요합니다.

이것은 **BrowserRouter의 기능이 아니라 웹 서버 또는 호스팅 환경의 설정**입니다.

---

# 19. 핵심 개념 정리

React Router를 단순히 "페이지를 이동하는 라이브러리"라고 이해하면 핵심을 놓치게 됩니다.

React Router의 본질은 다음과 같습니다.

> **브라우저의 현재 URL과 React UI를 연결하고, History API를 이용하여 새로운 HTML Document를 다시 로드하지 않으면서 URL 기반의 화면 전환을 구현하는 클라이언트 사이드 라우팅 시스템**

전체 구조를 압축하면 다음과 같습니다.

```text
                Browser
                   │
                   ▼
                  URL
                   │
                   ▼
             React Router
                   │
             Route Matching
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
        Home     About    Products
                            │
                            ▼
                       ProductDetail
                   │
                   ▼
             React Rendering
                   │
                   ▼
                  UI
```

그리고 그 아래에는 브라우저가 제공하는 History API가 존재합니다.

```text
React Router
     │
     ▼
History API
     │
     ├── pushState()
     ├── replaceState()
     └── popstate
     │
     ▼
Browser Session History
```

따라서 구조적으로는 다음과 같이 이해하면 가장 정확합니다.

```text
Browser History API
        ↓
React Router
        ↓
URL / Location
        ↓
Route Matching
        ↓
React Element
        ↓
React Rendering
        ↓
UI
```

# 마무리

React Router를 이해할 때 가장 중요한 것은 API를 외우는 것이 아닙니다.

다음 흐름을 이해하는 것이 핵심입니다.

```text
URL 변경
   ↓
Router가 현재 Location 확인
   ↓
Route Matching
   ↓
렌더링할 React Element 결정
   ↓
React 렌더링
   ↓
화면 변경
```

그리고 SPA 내부 navigation에서는:

```text
새 HTML Document 요청
        X

URL 변경
        +
React UI 변경
        O
```

이라는 차이가 있습니다.

결국 React Router의 핵심 철학은 다음 한 문장으로 정리할 수 있습니다.

> **URL을 애플리케이션 UI 상태의 일부로 사용하고, URL과 React 컴포넌트 트리를 동기화한다.**

이 개념을 이해하면 `Link`, `useNavigate`, `useParams`, `Outlet`, 중첩 Route 같은 기능들이 각각 따로 존재하는 API가 아니라 **하나의 URL → Route → UI 시스템을 구성하는 요소들**이라는 사실이 자연스럽게 연결됩니다.
