좋습니다. 기존 자료의 깊이는 유지하면서, **학생이 처음 접했을 때의 학습 순서**를 기준으로 전체 구조를 다시 잡았습니다. 특히 기존 자료에서 약했던 **Fiber → Commit → react-dom → 실제 DOM → 브라우저 렌더링** 연결을 독립적인 흐름으로 보강했고, `Lanes`, `Scheduler`, `Effect List`, `current/workInProgress` 관련 표현도 더 정확하게 정리했습니다. 

# React Fiber 완전 이해

React에서 다음 코드가 실행되었다고 생각해 봅시다.

```jsx
setCount(count + 1);
```

겉으로 보면 단순히 상태가 변경되고 화면의 숫자가 바뀌는 것처럼 보입니다.

하지만 React 내부에서는 훨씬 많은 작업이 발생합니다.

```text
State Update
     ↓
Update Scheduling
     ↓
Render Phase
     ↓
Fiber Reconciliation
     ↓
workInProgress Fiber Tree
     ↓
Commit Phase
     ↓
DOM Mutation
     ↓
Browser Rendering
     ↓
Screen
```

이 과정의 중심에 있는 React의 내부 아키텍처가 바로 **Fiber**입니다.

---

# 1. 먼저 전체 흐름부터 이해하자

React 컴포넌트를 다음과 같이 작성했다고 가정합니다.

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <h1>{count}</h1>
      <button onClick={() => setCount(count + 1)}>
        증가
      </button>
    </div>
  );
}
```

사용자가 버튼을 클릭하면 다음과 같은 흐름이 발생합니다.

```text
사용자 클릭
     ↓
onClick 실행
     ↓
setCount()
     ↓
Update 생성
     ↓
React가 업데이트 스케줄링
     ↓
Render Phase
     ↓
Counter() 다시 실행
     ↓
새 React Element 결과 계산
     ↓
Fiber Reconciliation
     ↓
변경할 Fiber에 flags 기록
     ↓
Render Phase 완료
     ↓
Commit Phase
     ↓
실제 DOM 변경
     ↓
브라우저 렌더링
     ↓
화면 변경
```

여기서 매우 중요한 것은 다음 두 작업을 구분하는 것입니다.

```text
React가
"무엇을 변경해야 하는가?"
계산하는 것

        ≠

실제 DOM을
변경하는 것
```

첫 번째 작업은 주로 **Render Phase**에서 이루어지고,

두 번째 작업은 **Commit Phase**에서 이루어집니다.

Fiber는 이 전체 과정을 가능하게 만드는 React 내부의 핵심 데이터 구조이자 작업 모델입니다.

---

# 2. React Fiber란 무엇인가?

Fiber를 단순히 하나의 자료구조라고만 설명하면 부족합니다.

Fiber는 크게 두 가지 의미를 가지고 있습니다.

> **Fiber = React 내부에서 UI를 표현하는 노드 구조 + 렌더링 작업 단위(Unit of Work)**

React는 컴포넌트와 Host Component 등의 정보를 Fiber Node라는 JavaScript 객체로 관리합니다.

그리고 이 Fiber Node들을 연결하여 **Fiber Tree**를 구성합니다.

개념적으로 보면 다음과 같습니다.

```text
<App />
   │
   ▼
App Fiber
   │
   ▼
Header Fiber
   │
   ▼
div Fiber
   │
   ├─────────────┐
   ▼             ▼
h1 Fiber     button Fiber
```

따라서 Fiber는 단순히 DOM을 복사한 트리가 아닙니다.

Fiber Node에는 다음과 같은 정보가 들어갑니다.

```text
Fiber Node
│
├─ 어떤 컴포넌트인가?
├─ 어떤 props를 가지고 있는가?
├─ 어떤 state를 가지고 있는가?
├─ 부모 Fiber는 누구인가?
├─ 자식 Fiber는 누구인가?
├─ 형제 Fiber는 누구인가?
├─ 실제 DOM과 어떻게 연결되는가?
├─ 어떤 업데이트가 필요한가?
├─ 업데이트의 우선순위는 무엇인가?
└─ Commit 단계에서 어떤 작업을 해야 하는가?
```

즉 Fiber는 React가 UI를 관리하기 위한 **내부 작업 노드**라고 이해하는 것이 좋습니다.

---

# 3. 왜 Fiber가 등장했는가?

React 15 이하에서는 이른바 **Stack Reconciler** 방식이 사용되었습니다.

렌더링 작업이 시작되면 트리를 재귀적으로 순회하면서 작업을 진행했습니다.

문제는 큰 렌더링 작업이 시작되면 React가 그 작업을 쉽게 중단할 수 없었다는 것입니다.

```text
Rendering Start
      ↓
Component A
      ↓
Component B
      ↓
Component C
      ↓
Component D
      ↓
Component E
      ↓
Rendering End
```

트리가 크고 계산량이 많다면 JavaScript 메인 스레드를 오랫동안 점유할 수 있습니다.

브라우저의 메인 스레드는 React만 사용하는 것이 아닙니다.

```text
Main Thread

JavaScript
Event Handling
React Rendering
Style Calculation
Layout
Paint 관련 작업
...
```

따라서 React가 오랫동안 메인 스레드를 점유하면 사용자 입력 처리 등이 지연될 수 있습니다.

Fiber 아키텍처의 중요한 목표 중 하나는 큰 렌더링 작업을 **작은 작업 단위**로 표현할 수 있도록 만드는 것입니다.

```text
큰 Render 작업

        ↓

Fiber A
Fiber B
Fiber C
Fiber D
Fiber E
...
```

이 구조를 기반으로 React는 렌더링 작업에 우선순위를 부여하고, 특정 종류의 concurrent rendering에서는 필요할 경우 작업을 양보하거나 다시 시작할 수 있습니다.

---

# 4. Fiber Node의 구조

실제 Fiber 구조는 매우 복잡하지만 개념적으로 단순화하면 다음과 같습니다.

```js
type Fiber = {

  // Fiber 종류
  tag: WorkTag,

  // 컴포넌트 함수, 클래스 또는 'div' 같은 Host Component 타입
  type: any,

  key: null | string,

  // Fiber Tree 연결
  child: Fiber | null,
  sibling: Fiber | null,
  return: Fiber | null,

  // props / state
  pendingProps: any,
  memoizedProps: any,
  memoizedState: any,

  // 업데이트
  updateQueue: any,

  // 우선순위
  lanes: Lanes,

  // 실제 Host 객체 또는 클래스 인스턴스
  stateNode: any,

  // Commit에서 처리할 작업
  flags: Flags,
  subtreeFlags: Flags,

  // current ↔ workInProgress 연결
  alternate: Fiber | null
};
```

핵심 필드만 분류하면 다음과 같습니다.

| 영역            | 주요 필드                           | 역할              |
| ------------- | ------------------------------- | --------------- |
| Fiber 종류      | `tag`, `type`                   | 어떤 종류의 노드인지 표현  |
| Tree          | `child`, `sibling`, `return`    | Fiber Tree 구조   |
| Props         | `pendingProps`, `memoizedProps` | 새로운/기존 props    |
| State         | `memoizedState`                 | Hook 및 state 정보 |
| Update        | `updateQueue`                   | 처리해야 할 업데이트     |
| Priority      | `lanes`                         | 작업 우선순위         |
| Host 연결       | `stateNode`                     | 실제 DOM 노드 등과 연결 |
| Commit        | `flags`, `subtreeFlags`         | 필요한 변경 작업 표시    |
| Double Buffer | `alternate`                     | 두 Fiber 버전 연결   |

---

# 5. Fiber Tree는 일반적인 DOM Tree와 다르다

React Element가 다음과 같다고 생각해 봅시다.

```jsx
<div>
  <h1>Hello</h1>
  <button>Click</button>
</div>
```

Fiber는 일반적인 `children[]` 배열만으로 트리를 순회하는 방식이 아니라 다음과 같은 연결 구조를 사용합니다.

```text
            div Fiber
                │
              child
                ↓
             h1 Fiber
                │
             sibling
                ↓
           button Fiber
```

각 Fiber는 대표적으로 다음 관계를 가집니다.

```text
child
  ↓
첫 번째 자식

sibling
  ↓
다음 형제

return
  ↓
부모
```

예를 들어:

```text
               App
                │
              child
                ▼
               div
                │
              child
                ▼
               h1
                │
             sibling
                ▼
              button
```

이 구조 덕분에 React는 Fiber 하나를 **하나의 작업 단위**로 다룰 수 있습니다.

---

# 6. current와 workInProgress

Fiber를 이해할 때 매우 중요한 개념이 **Double Buffering**입니다.

React는 렌더링 과정에서 논리적으로 두 버전의 Fiber Tree를 다룹니다.

```text
current Fiber Tree

현재 Commit된 UI 상태를 표현

          │
          │ Update
          ▼

workInProgress Fiber Tree

다음 UI 상태를 계산
```

각 Fiber는 `alternate`를 통해 대응되는 Fiber와 연결될 수 있습니다.

```text
current Fiber
     │
     │ alternate
     ▼
workInProgress Fiber

workInProgress Fiber
     │
     │ alternate
     ▼
current Fiber
```

중요한 점은 **매번 Fiber Tree 전체를 완전히 새로운 객체들로 만드는 개념이 아니라는 것**입니다.

React는 기존 Fiber와 `alternate` 구조를 이용해 작업용 Fiber를 재사용합니다.

---

# 7. Fiber Tree와 DOM Tree는 다른 것이다

여기서 반드시 구분해야 합니다.

```text
Fiber Tree
     ≠
DOM Tree
```

Fiber Tree는 React 내부 데이터 구조입니다.

DOM Tree는 브라우저가 관리하는 실제 문서 객체 구조입니다.

```text
React

Fiber Tree
     │
     │ Commit
     ▼

react-dom
     │
     │ DOM API
     ▼

Browser

DOM Tree
```

따라서

```text
workInProgress
      ↓
current
```

전환과

```text
DOM Mutation
```

은 관련되어 있지만 **동일한 개념이 아닙니다.**

---

# 8. Render Phase

업데이트가 발생하면 React는 새로운 UI 상태를 계산해야 합니다.

이 작업이 주로 **Render Phase**에서 이루어집니다.

Render Phase의 목표는 다음과 같습니다.

> 다음 UI 상태를 나타낼 workInProgress Fiber Tree를 계산하고, Commit 단계에서 수행해야 할 변경 작업을 기록한다.

대표적인 내부 작업 흐름을 단순화하면 다음과 같습니다.

```text
Render Phase

workInProgress
      ↓
beginWork()
      ↓
자식 계산
      ↓
Reconciliation
      ↓
다음 Fiber
      ↓
...
      ↓
completeWork()
      ↓
flags / subtreeFlags 계산
      ↓
Render Phase 완료
```

Render Phase에서는 실제 DOM을 직접 변경하지 않습니다.

```text
Render Phase

DOM Mutation
     X
```

이 특징이 매우 중요합니다.

특정 concurrent rendering에서는 Render Phase의 작업이 중단되거나 다시 시작되거나 폐기될 수 있기 때문입니다.

---

# 9. Render Phase는 왜 순수해야 하는가?

컴포넌트 함수는 Render Phase에서 실행될 수 있습니다.

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  return <h1>{count}</h1>;
}
```

Render Phase는 다시 실행될 가능성이 있기 때문에 렌더링 로직은 가능한 한 **순수해야 합니다.**

잘못된 예:

```jsx
let sequence = 0;

function BadComponent() {

  sequence++;

  return <p>{sequence}</p>;
}
```

컴포넌트가 다시 렌더링되면 외부 값까지 변경됩니다.

렌더링은 UI 계산 과정이어야 합니다.

개념적으로는 다음 관계를 유지하는 것이 좋습니다.

```text
UI = f(props, state)
```

즉 동일한 props와 state에 대해서 렌더링 로직이 예측 가능한 결과를 만들어야 합니다.

---

# 10. Reconciliation

Render Phase에서 매우 중요한 작업이 **Reconciliation**입니다.

React는 이전 Fiber 구조와 새롭게 계산된 React Element 정보를 비교하여 기존 Fiber를 재사용할 것인지 결정합니다.

핵심 기준 중 하나가 다음 두 가지입니다.

```text
type
+
key
```

예를 들어:

```jsx
<UserProfile key="100" />
```

이전에도

```jsx
<UserProfile key="100" />
```

였다면 React는 기존 Fiber를 재사용할 가능성이 높습니다.

반면 다음처럼 타입이 변경되면:

```jsx
<div>
```

↓

```jsx
section>
```

React는 기존 Host Fiber를 그대로 유지할 수 없습니다.

---

# 11. 리스트에서 key가 중요한 이유

다음 코드가 있다고 생각해 봅시다.

```jsx
<ul>
  {items.map(item => (
    <li key={item.id}>
      {item.name}
    </li>
  ))}
</ul>
```

`key`는 같은 부모 아래의 형제들 사이에서 React가 기존 Fiber와 새로운 Element를 대응시키는 데 사용됩니다.

```text
Previous

key=10
key=20
key=30


Next

key=30
key=10
key=20
```

React는 key를 이용하여 각각이 어떤 항목에 대응하는지 판단할 수 있습니다.

따라서 key는 단순한 성능 최적화 옵션이 아닙니다.

**컴포넌트의 identity와 state 보존 여부를 결정하는 중요한 정보**입니다.

---

# 12. Fiber의 flags

Render Phase에서 React는 DOM을 바로 변경하지 않습니다.

대신 Fiber에

> "Commit Phase에서 어떤 작업이 필요한가?"

를 기록합니다.

대표적인 예가 `flags`입니다.

개념적으로 다음과 같이 생각할 수 있습니다.

```text
Fiber
│
├─ Placement
│    새 Host 노드를 삽입해야 함
│
├─ Update
│    기존 Host 노드를 수정해야 함
│
└─ ChildDeletion
     자식을 제거해야 함
```

예를 들어:

```jsx
<h1>Hello</h1>
```

가

```jsx
<h1>Hello React</h1>
```

로 변경되었다면 Render Phase에서 변경 필요성을 계산합니다.

하지만 이 순간 실제 DOM을 바로 변경하지는 않습니다.

```text
Render Phase

Old Fiber
     ↓
Reconciliation
     ↓
New Fiber
     ↓
Update 필요
     ↓
flags에 기록
```

---

# 13. subtreeFlags

React는 자식 Fiber에서 발생한 작업 정보를 부모 쪽으로 모읍니다.

```text
          Parent
             │
       subtreeFlags
             │
      ┌──────┴──────┐
      ▼             ▼
   Child A       Child B
   Update        No Work
```

이를 통해 Commit 단계에서 변경 작업이 없는 서브트리를 불필요하게 모두 탐색하는 것을 줄일 수 있습니다.

과거 React 구현에서는 Commit 대상들을 연결한 선형 **effect list**가 사용되었습니다.

하지만 현대 React의 Commit traversal에서는 `flags`와 `subtreeFlags`를 활용하여 필요한 서브트리를 찾아가는 구조가 사용됩니다.

따라서 오래된 React 설명에서 등장하는 `nextEffect` 기반 effect list와 현재의 Hook effect 구조를 같은 것으로 이해하면 안 됩니다.

---

# 14. Commit Phase

Render Phase가 성공적으로 완료되면 React는 계산된 변경사항을 실제 환경에 반영합니다.

이 단계가 **Commit Phase**입니다.

```text
Render Phase

"무엇을 바꿀 것인가?"

        ↓

Commit Phase

"실제로 바꾼다"
```

Commit Phase는 Render Phase와 성격이 다릅니다.

```text
Render Phase
────────────────
계산 중심
DOM 직접 변경 X
작업이 다시 실행될 수 있음
일부 concurrent 작업은 중단/폐기 가능


Commit Phase
────────────────
실제 변경 수행
DOM Mutation 발생
일관성을 위해 동기적으로 처리
```

---

# 15. Commit Phase의 주요 단계

개념적으로 Commit Phase는 다음과 같은 단계들로 이해할 수 있습니다.

```text
Commit Phase
      │
      ▼
Before Mutation
      │
      ▼
Mutation
      │
      ▼
Fiber current 전환과 관련된 처리
      │
      ▼
Layout
      │
      ▼
Passive Effects
```

## Before Mutation

DOM을 변경하기 전에 필요한 작업을 처리합니다.

클래스 컴포넌트의 대표적인 예는:

```text
getSnapshotBeforeUpdate()
```

입니다.

---

# 16. Mutation Phase — 실제 DOM이 변경되는 순간

여기가 매우 중요합니다.

Render Phase에서 Fiber에 기록해 두었던 변경사항을 기반으로 실제 Host 환경을 변경합니다.

웹에서는 Host 환경이 **DOM**입니다.

전체 관계를 단순화하면 다음과 같습니다.

```text
Fiber flags
      ↓
React Reconciler
      ↓
React DOM Host Config
      ↓
Browser DOM API
      ↓
Actual DOM Tree
```

예를 들어 Fiber가 다음 작업을 나타낸다고 생각해 봅시다.

```text
Placement
```

React DOM은 웹 환경에서 이에 대응하는 Host 작업을 수행합니다.

개념적으로 결국 브라우저의 DOM 조작과 연결됩니다.

```js
parent.appendChild(node);
```

또는

```js
parent.insertBefore(node, before);
```

삭제가 필요하다면 개념적으로:

```js
parent.removeChild(node);
```

속성 변경 역시 DOM의 속성/프로퍼티 변경으로 이어집니다.

즉,

> **Fiber 자체가 DOM은 아니며, Fiber에 계산된 변경사항을 Commit Phase에서 React DOM이 브라우저의 DOM 조작 기능을 통해 실제 DOM에 반영합니다.**

---

# 17. React Reconciler와 React DOM의 역할 차이

여기서 React의 구조를 한 단계 더 정확하게 볼 필요가 있습니다.

```text
React Component
      ↓
React Element
      ↓
React Reconciler
      ↓
Fiber
      ↓
"어떤 Host 변경이 필요한가?"
      ↓
Renderer
```

웹에서는 Renderer가 `react-dom`입니다.

```text
React Reconciler
      │
      │ Host 작업 요청
      ▼
react-dom
      │
      │ Browser DOM 조작
      ▼
DOM
```

React Reconciler의 핵심 관심사는:

> 무엇을 변경해야 하는가?

입니다.

React DOM의 관심사는:

> 웹 브라우저에서 그 변경을 어떻게 적용할 것인가?

입니다.

이 구분은 React가 DOM 이외의 Host 환경에서도 사용될 수 있는 이유를 이해하는 데 중요합니다.

---

# 18. DOM Mutation 이후 브라우저에서 일어나는 일

React가 DOM을 변경했다고 해서 React가 직접 픽셀을 그리는 것은 아닙니다.

그 이후는 브라우저 렌더링 엔진의 영역입니다.

```text
React
────────────────────────────

Render Phase
      ↓
Fiber Reconciliation
      ↓
Commit Phase
      ↓
DOM Mutation


Browser
────────────────────────────

DOM Tree
      │
      ├──────────────┐
      │              │
      ▼              ▼
                    CSSOM
      │              │
      └──────┬───────┘
             ▼
      Style Calculation
             ↓
        Layout Tree
             ↓
           Layout
             ↓
           Paint
             ↓
          Raster
             ↓
        Composite
             ↓
           Screen
```

따라서 React의 역할과 브라우저의 역할을 구분해야 합니다.

```text
React
────────────────────
UI 변경 계산
Fiber 관리
Reconciliation
DOM Mutation 수행 요청


Browser
────────────────────
DOM 관리
Style Calculation
Layout
Paint
Raster
Composite
Screen 출력
```

# 19. Fiber의 current 전환

Commit 과정이 진행되면서 완성된 Fiber Tree는 새로운 current가 됩니다.

개념적으로:

```text
Before Commit

current
   │
   │ alternate
   ▼
workInProgress


Commit


After Commit

finishedWork
     ↓
new current
```

여기서 주의해야 합니다.

```text
Fiber current 전환
        ≠
DOM Tree 자체를 Fiber Tree로 교체
```

DOM Tree는 브라우저가 관리합니다.

React는 필요한 DOM Mutation을 수행하고 내부적으로 새로운 Fiber Tree를 current로 사용하게 됩니다.

# 20. Layout Effects

DOM Mutation 이후에는 변경된 DOM을 기반으로 동기적으로 실행되어야 하는 작업이 있습니다.

대표적인 것이:

```jsx
useLayoutEffect(() => {

  const rect =
    elementRef.current.getBoundingClientRect();

});
```

입니다.

개념적으로:

```text
DOM Mutation
      ↓
DOM 변경 완료
      ↓
Layout Effects
      ↓
useLayoutEffect
```

`useLayoutEffect`는 DOM 변경 이후, 브라우저가 사용자에게 최종 화면을 보여주기 전에 DOM을 읽거나 동기적인 조정을 수행해야 할 때 사용됩니다.

너무 무거운 작업을 수행하면 화면 표시를 지연시킬 수 있으므로 주의해야 합니다.

---

# 21. useEffect는 어디에서 실행되는가?

`useEffect`는 `useLayoutEffect`와 실행 시점이 다릅니다.

개념적으로:

```text
Commit
  ↓
DOM Mutation
  ↓
Layout Effects
  ↓
Browser가 화면을 표시할 기회를 가짐
  ↓
Passive Effects
  ↓
useEffect
```

따라서 일반적인 side effect에는 `useEffect`를 사용하는 것이 기본입니다.

```jsx
useEffect(() => {

  // subscription
  // synchronization
  // 외부 시스템과의 연결

}, []);
```

---

# 22. Hook 상태는 어디에 저장되는가?

함수 컴포넌트에는 클래스 컴포넌트처럼 인스턴스 객체가 없습니다.

그렇다면 `useState()`의 상태는 어디에 저장될까요?

Fiber와 연결된 Hook 구조에 저장됩니다.

개념적으로:

```text
Function Component Fiber
          │
          │ memoizedState
          ▼
        Hook 1
          │
          ▼
        Hook 2
          │
          ▼
        Hook 3
          │
          ▼
         ...
```

단순화한 Hook 구조는 다음과 같습니다.

```js
type Hook = {

  memoizedState: any,

  baseState: any,

  baseQueue: Update | null,

  queue: UpdateQueue | null,

  next: Hook | null
};
```

---

# 23. Hook 호출 순서가 중요한 이유

다음 컴포넌트를 봅시다.

```jsx
function Example() {

  const [name, setName] = useState('');
  const [age, setAge] = useState(0);

  useEffect(() => {
    console.log(name);
  }, [name]);

  return ...;
}
```

Fiber 내부에서는 개념적으로 다음과 같이 대응됩니다.

```text
fiber.memoizedState
        │
        ▼
Hook 1
useState(name)
        │
        ▼
Hook 2
useState(age)
        │
        ▼
Hook 3
useEffect(...)
```

React는 Hook을 이름으로 찾아가는 것이 아니라 **호출 순서에 기반하여 대응시킵니다.**

그래서 다음과 같은 코드는 문제가 됩니다.

```jsx
if (condition) {
  useState(10);
}
```

조건에 따라 Hook 호출 순서가 달라질 수 있기 때문입니다.

이것이 Hooks를 조건문이나 반복문 내부에서 임의로 호출하면 안 되는 핵심 이유입니다.

---

# 24. Hook과 Double Buffering

좀 더 정확하게 보면 current Fiber와 workInProgress Fiber가 있기 때문에 Hook 상태 역시 렌더링 과정에서 두 Fiber 버전과 연관됩니다.

```text
current Fiber
     │
     │ Hook State
     ▼
Current Hook List


        Render


workInProgress Fiber
     │
     │ 새 렌더 결과
     ▼
WorkInProgress Hook List
```

따라서 진행 중인 렌더가 폐기되더라도 이미 Commit된 current 상태를 보호할 수 있습니다.

---

# 25. Effects와 Fiber

`useEffect()`를 호출하면 React는 해당 컴포넌트와 연결된 Hook/effect 정보를 기록합니다.

또한 Fiber에는 해당 종류의 Commit 작업이 필요하다는 정보가 flags를 통해 표시됩니다.

중요한 것은 두 개념을 구분하는 것입니다.

```text
과거 React의
nextEffect 기반 Fiber Effect List

        ≠

Hook에서 관리되는
useEffect 관련 Effect 구조
```

현대 React의 Commit traversal은 Fiber의 `flags`와 `subtreeFlags`를 활용합니다.

반면 함수 컴포넌트의 `useEffect` 관련 정보는 해당 Fiber와 연결된 Hook/update 구조를 통해 관리됩니다.

---

# 26. Lanes — 업데이트 우선순위

모든 업데이트가 똑같이 중요한 것은 아닙니다.

예를 들어 사용자가 검색창에 문자를 입력한다고 생각해 봅시다.

```jsx
function handleChange(e) {

  setInput(e.target.value);

  startTransition(() => {
    setSearchResult(
      heavySearch(e.target.value)
    );
  });
}
```

두 업데이트의 성격이 다릅니다.

```text
setInput()
     ↓
사용자의 직접적인 입력 반영
     ↓
높은 응답성이 중요


setSearchResult()
     ↓
무거운 결과 UI 업데이트
     ↓
Transition으로 표시 가능
```

React는 **Lanes**라는 비트마스크 기반 모델을 사용하여 업데이트의 우선순위와 처리 관계를 표현합니다.

개념적으로:

```text
Pending Updates

Lane A ── 사용자 입력 관련
Lane B ── 일반 업데이트
Lane C ── Transition
Lane D ── 기타 작업
```

실제 Lane 시스템은 이것보다 훨씬 복잡하지만 핵심은 다음과 같습니다.

> React는 모든 업데이트를 하나의 동일한 작업으로 취급하지 않고, 업데이트의 성격과 우선순위를 구분하여 관리한다.

---

# 27. Scheduler와 Lanes는 같은 것이 아니다

이 부분은 자주 혼동됩니다.

```text
Lanes
────────────────────

Reconciler 관점

"이 업데이트는
어떤 우선순위와
처리 관계를 가지는가?"


Scheduler
────────────────────

실행 스케줄 관점

"예약된 작업을
언제 실행하고
언제 양보할 것인가?"
```

즉:

```text
Update
   ↓
Lane 결정
   ↓
Reconciler
   ↓
필요한 작업 Scheduling
   ↓
Scheduler
   ↓
실행
```

두 시스템은 서로 협력하지만 동일한 개념은 아닙니다.

---

# 28. Time Slicing

Fiber가 작업 단위이기 때문에 React는 특정 concurrent rendering에서 여러 Fiber 작업을 처리하다가 필요하면 제어권을 양보할 수 있습니다.

개념적으로:

```js
function workLoopConcurrent() {

  while (
    workInProgress !== null &&
    !shouldYield()
  ) {

    performUnitOfWork(workInProgress);
  }
}
```

개념적 흐름은 다음과 같습니다.

```text
Fiber A 처리
     ↓
Fiber B 처리
     ↓
Fiber C 처리
     ↓
shouldYield?
     ↓
    YES
     ↓
브라우저에게 제어권 양보
     ↓
나중에 작업 재개
     ↓
Fiber D
     ↓
Fiber E
```

이런 형태의 작업 분할과 양보가 **Time Slicing**의 핵심 아이디어입니다.

---

# 29. 모든 setState가 자동으로 Time Slicing되는 것은 아니다

이 부분은 매우 중요합니다.

React 18+를 사용한다고 해서 모든 상태 업데이트가 자동으로 일정 시간마다 잘려서 실행되는 것은 아닙니다.

업데이트가 어떤 상황에서 발생했는지, 어떤 Lane을 부여받았는지, 현재 렌더링 모드와 우선순위가 무엇인지 등에 따라 처리 방식이 달라질 수 있습니다.

`startTransition()`은 개발자가 다음과 같은 의도를 React에게 알려주는 대표적인 API입니다.

```text
"이 업데이트는
사용자의 즉각적인 입력보다
덜 급하다."
```

예:

```jsx
setInput(value);

startTransition(() => {
  setResults(expensiveFilter(value));
});
```

그러면 긴 Transition 렌더링이 진행되는 동안 더 중요한 업데이트가 들어왔을 때 React가 우선순위를 조정할 수 있습니다.

따라서 다음과 같이 이해하는 것이 좋습니다.

```text
잘못된 이해

React 18
   ↓
모든 Render가 자동 Time Slicing


올바른 이해

React의 concurrent architecture
   ↓
업데이트 Priority / Lane
   ↓
렌더링 상황
   ↓
필요한 경우
interruptible rendering 가능
```

---

# 30. Scheduler의 구현 세부사항은 핵심 개념과 분리해서 보자

Scheduler는 React가 메인 스레드에서 작업을 수행하면서 필요할 경우 브라우저에게 제어권을 양보하고 이후 작업을 계속할 수 있도록 지원합니다.

다만 여기서 주의할 점이 있습니다.

`MessageChannel`, 특정 yield 시간 등의 내용은 React 버전과 구현에 따라 변경될 수 있는 **implementation detail**입니다.

따라서 Fiber를 이해할 때 핵심은 특정 API 이름이 아니라 다음 구조입니다.

```text
React Work
    ↓
일정량 작업
    ↓
계속 실행해도 되는가?
    ↓
YES ─────→ 계속 작업

NO
 ↓
Host에게 제어권 양보
 ↓
이후 작업 재개
```

이 원리를 먼저 이해하는 것이 중요합니다.

---

# 31. Concurrent Rendering과 Fiber

Fiber가 중요한 가장 큰 이유 중 하나는 React가 렌더링 작업을 세밀한 작업 단위로 관리할 수 있다는 것입니다.

이를 기반으로 React는:

```text
작업을 작은 단위로 표현
        ↓
우선순위 관리
        ↓
필요하면 작업 양보
        ↓
나중에 재개
        ↓
필요 없어진 Render는 폐기
        ↓
새로운 Render 시작
```

같은 전략을 사용할 수 있습니다.

이러한 기반 위에서 다음과 같은 React 기능들이 동작합니다.

```text
startTransition

useDeferredValue

Suspense

Selective Hydration

기타 Concurrent Features
```

예전 자료에서 사용되던 **Concurrent Mode**라는 하나의 전역 모드를 켜고 끈다는 식의 설명보다는, 현대 React에서는 이러한 concurrent 기능과 렌더링 아키텍처를 중심으로 이해하는 것이 적절합니다.

# 34. React와 브라우저의 경계

전체 구조를 다시 보면 React가 어디까지 담당하는지가 명확해집니다.

```text

│              React              │
│                                 │
│ State Update                    │
│      ↓                          │
│ Scheduling                      │
│      ↓                          │

│      ↓                          │

│      ↓                          │

                │ DOM API
```

# 35. 최종 핵심 정리

## 1. Fiber

Fiber는 React 내부의 **노드 구조이자 작업 단위**입니다.

```text
Fiber
=
UI 내부 표현
+
Render 작업 단위
```

---

## 2. Fiber Tree

Fiber Node들은 다음 포인터를 통해 트리를 구성합니다.

```text
child
sibling
return
```

---

## 3. Double Buffering

React는 렌더링 과정에서:

```text
current
+
workInProgress
```

두 Fiber 버전을 관리하며 `alternate`를 통해 서로 대응시킬 수 있습니다.

---

## 4. Render Phase

Render Phase에서는:

```text
Component 실행
     ↓
React Element 계산
     ↓
Reconciliation
     ↓
Fiber 계산
     ↓
flags 기록
```

이 이루어집니다.

**실제 DOM Mutation은 이 단계에서 발생하지 않습니다.**

---

## 5. Commit Phase

Commit Phase에서는 Render Phase에서 계산한 결과를 실제 Host 환경에 반영합니다.

웹에서는:

```text
Fiber flags
     ↓
React Reconciler
     ↓
react-dom
     ↓
DOM operations
     ↓
Actual DOM
```

으로 연결됩니다.

---

## 6. DOM Mutation 이후

DOM이 변경되면 브라우저 렌더링 시스템이 필요에 따라 후속 작업을 수행합니다.

```text
DOM
 +
CSSOM
 ↓
Style Calculation
 ↓
Layout
 ↓
Paint
 ↓
Raster
 ↓
Composite
 ↓
Screen
```

---

## 7. Reconciliation

기존 Fiber와 새로운 React Element를 비교하면서 기존 Fiber를 재사용할 것인지 판단합니다.

특히 children reconciliation에서 중요한 기준은:

```text
type
+
key
```

입니다.

---

## 8. Hooks

함수 컴포넌트의 Hook 상태는 Fiber와 연결된 Hook 구조를 통해 관리됩니다.

```text
Fiber
  ↓
memoizedState
  ↓
Hook
  ↓
Hook
  ↓
Hook
```

따라서 Hook 호출 순서가 중요합니다.

---

## 9. Effects

`useEffect`, `useLayoutEffect`에 필요한 정보 역시 Fiber 및 Hook 구조와 연결되어 관리됩니다.

Fiber의 flags를 통해 Commit 단계에서 필요한 effect 처리를 식별합니다.

---

## 10. Lanes

React는 Lanes를 이용하여 업데이트의 우선순위와 처리 관계를 관리합니다.

```text
Update
 ↓
Lane
 ↓
Scheduling
 ↓
Rendering
```

---

## 11. Concurrent Rendering

Fiber는 렌더링 작업을 작은 작업 단위로 관리할 수 있게 합니다.

이를 기반으로 특정 concurrent rendering에서 React는:

```text
작업
 ↓
중단
 ↓
양보
 ↓
재개
```

하거나,

```text
기존 Render 폐기
      ↓
새로운 Render 시작
```

같은 전략을 사용할 수 있습니다.

---

# 36. Fiber를 한 문장으로 정의한다면

> **React Fiber는 컴포넌트의 props, state, Hook, 부모·자식 관계, Host 객체 연결, 업데이트 우선순위와 Commit 작업 정보 등을 관리하면서 React가 렌더링 작업을 작은 단위로 계산하고 스케줄링할 수 있도록 만든 내부 아키텍처이다.**

그리고 전체 React 렌더링을 한 문장으로 표현하면:

> **React는 상태 변경이 발생하면 Fiber를 기반으로 다음 UI를 계산하고(Render Phase), 필요한 변경사항을 Commit Phase에서 `react-dom`을 통해 실제 DOM에 반영하며, 이후 브라우저가 Style Calculation → Layout → Paint → Raster → Composite 과정을 거쳐 최종 화면을 만든다.**

따라서 React를 깊이 이해하려면 다음 흐름을 하나의 연결된 시스템으로 이해해야 합니다.

```text
State
  ↓
React Element
  ↓
Fiber
  ↓
Reconciliation
  ↓
Render Phase
  ↓
Commit Phase
  ↓
react-dom
  ↓
DOM
  ↓
Browser Rendering Pipeline
  ↓
Screen
```

이것이 **React Fiber를 중심으로 본 React 렌더링의 전체 구조**입니다.
