React의 DOM 처리 방식은 **전통적인 직접 DOM 조작 방식과 완전히 다릅니다.**
React는 성능 최적화와 선언적 UI 구성을 위해 **Virtual DOM (가상 DOM)** 을 중심으로 작동하며,
이를 통해 실제 DOM 조작을 **최소화**하고 **효율적인 상태 기반 렌더링**을 가능하게 합니다.

다음은 React의 DOM 처리 방식을 전문가 수준으로 상세히 설명한 내용입니다.

---

## 1. 기본 철학: 선언형 UI + 상태 기반 DOM 렌더링

React는 다음 철학을 바탕으로 DOM을 처리합니다:

* **“DOM은 상태(state)의 함수이다.”**
* `UI = f(state)`로, 상태가 바뀌면 전체 UI를 다시 그리는 것처럼 동작
* 하지만 실제로는 모든 DOM을 새로 그리는 것이 아니라 **Virtual DOM 기반 diffing**으로 최소 변경만 수행

---

## 2. Virtual DOM: 가상 DOM 트리

### Virtual DOM이란?

* 브라우저의 실제 DOM을 **메모리 상에서 JavaScript 객체 형태로 추상화한 트리 구조**
* React 엘리먼트(`React.createElement` 또는 JSX)로 생성됨
* 실제 DOM과 동일한 구조를 가지되, **실제 브라우저 DOM이 아님**

### 예시:

```jsx
const element = <h1>Hello, world</h1>;
```

→ React는 내부적으로 다음처럼 구성:

```js
const virtualDom = {
  type: 'h1',
  props: {
    children: 'Hello, world'
  }
};
```

---

## 3. Reconciliation (조정): Virtual DOM 비교 알고리즘

### 상태가 변경되면:

1. 새로운 Virtual DOM 생성
2. 이전 Virtual DOM과 **Diffing Algorithm**으로 비교
3. 차이를 계산
4. 최소한의 실제 DOM 조작 수행 (patching)

### 이 과정을 React는 **Reconciliation**이라고 부릅니다.

---

## 4. Diffing Algorithm: 효율적인 변경 감지

일반적인 트리 비교는 **O(n³)** 이지만, React는 두 가지 **휴리스틱(가정)** 을 도입해 이를 **O(n)** 으로 낮춥니다:

* **① 노드 타입이 다르면** → 비교를 포기하고 **그 아래 서브트리 전체를 폐기 후 재생성**
  * 단순 교체가 아니라 **자식들의 state, DOM 노드, ref가 전부 파괴**됩니다.
  * `<div>` → `<span>`, `<Counter>` → `<OtherCounter>` 모두 해당됩니다.
* **② 같은 타입이면** → 기존 노드/state를 유지하고 달라진 props만 갱신
* **③ 형제 목록은 `key`로 매칭** → 순서가 바뀌어도 같은 key면 같은 요소로 보고 재사용

### key에 대한 흔한 오해

* key는 **형제(sibling) 사이에서만** 유효합니다. 전역 고유 ID일 필요가 없습니다.
* key 없이 배열을 렌더하면 React는 **인덱스 순서로 매칭**합니다.
  → 목록 앞에 항목을 추가/삭제하거나 정렬이 바뀌면 **잘못된 노드끼리 매칭되어**
  input 값이나 자식 컴포넌트 state가 엉뚱한 행으로 옮겨갑니다.
* 반대로 이 성질을 이용해 **key를 일부러 바꿔서 컴포넌트 state를 강제로 초기화**하는 기법도 자주 씁니다.

```jsx
// userId가 바뀌면 Profile 내부 state를 통째로 리셋
<Profile key={userId} userId={userId} />
```

### 그리고 "최소한의 DOM 조작"은 최적해가 아닙니다

위 휴리스틱은 **정확한 최소 편집 스크립트를 구하지 않습니다.**
같은 UI라도 트리 구조를 어떻게 짜느냐에 따라 재생성 범위가 달라지므로,
조건부 렌더링에서 **감싸는 태그를 바꾸는 코드**는 피하는 편이 좋습니다.

## 5. 실제 DOM 반영: React DOM Renderer

React는 플랫폼에 따라 다른 **Renderer**를 사용합니다:

| Renderer            | 설명                    |
| ------------------- | --------------------- |
| `react-dom`         | 브라우저용 실제 DOM 조작 수행    |
| `react-native`      | 네이티브 컴포넌트로 렌더링        |
| `react-three-fiber` | WebGL 기반 Three.js 엔진용 |
| `ink`               | 터미널 기반 CLI UI를 위한 렌더러 |

### 예: react-dom (React 19 기준)

```jsx
import { createRoot } from 'react-dom/client';

const root = createRoot(document.getElementById('root'));
root.render(<App />);
```

* `App` → Virtual DOM 생성
* Virtual DOM diff → 실제 DOM 변경

### React 19에서 제거된 레거시 API

React 18에서 deprecated 경고가 뜨던 아래 API들은 **React 19에서 완전히 제거**되었습니다.

| 제거됨 (React 18까지)                | 대체 (React 19)                                    |
| ------------------------------- | ------------------------------------------------ |
| `ReactDOM.render(el, container)`   | `createRoot(container).render(el)`                |
| `ReactDOM.hydrate(el, container)`  | `hydrateRoot(container, el)`                      |
| `ReactDOM.unmountComponentAtNode` | `root.unmount()`                                  |
| `ReactDOM.findDOMNode`            | ref 사용                                            |
| `react-dom/server`의 `renderToString`은 유지되나, `renderToNodeStream` 제거 | `renderToPipeableStream` / `renderToReadableStream` |

* 임포트 경로도 중요합니다. 클라이언트 렌더링 API는 `react-dom`이 아니라 **`react-dom/client`** 에 있습니다.
* `createRoot`로 만든 root는 **동시성 렌더링(Concurrent Rendering)이 기본 활성화**됩니다.
  (구 `ReactDOM.render`는 레거시 동기 모드였고, 이것이 18에서 root API를 분리한 이유입니다.)

```jsx
// SSR 결과에 이벤트를 붙이는 경우
import { hydrateRoot } from 'react-dom/client';
hydrateRoot(document.getElementById('root'), <App />);
```

## 6. Batching & Fiber Architecture

### Batching (일괄 처리)

* 여러 상태 변화가 동시에 일어나면 **한 번의 렌더링으로 묶어서 처리**
* 불필요한 리렌더링 방지

**React 18부터는 Automatic Batching**입니다. React 17까지는 **React 이벤트 핸들러 안에서만** 배칭되었고,
`setTimeout`, `Promise.then`, 네이티브 이벤트 리스너 안에서는 `setState` 하나마다 렌더가 발생했습니다.

```jsx
// React 17: 2번 렌더 / React 18~19: 1번 렌더
setTimeout(() => {
  setCount(c => c + 1);
  setFlag(f => !f);
}, 0);
```

배칭을 **강제로 깨야 할 때**만 `flushSync`를 사용합니다.
(DOM을 즉시 읽어야 하는 측정 코드, 서드파티 라이브러리 연동 등)

```jsx
import { flushSync } from 'react-dom';

flushSync(() => {
  setCount(c => c + 1);
});
// 이 시점에는 DOM이 이미 갱신되어 있음
console.log(listRef.current.scrollHeight);
```

> `flushSync`는 동시성 최적화를 무력화하고 동기 렌더를 강제하므로 **성능 탈출구**로만 쓰세요.

### React Fiber

React 16 이후 도입된 **새로운 Reconciliation 엔진**

* Virtual DOM 계산을 Fiber 노드 단위의 **작업 단위(Unit of Work)** 로 쪼갬
* **Lane(비트마스크) 기반 우선순위 스케줄링** — 사용자 입력은 높은 lane, `startTransition`으로 감싼
  무거운 업데이트는 낮은 lane으로 분류해 뒤로 미룸
  (React 17까지 쓰이던 `expirationTime` 모델은 18에서 Lanes로 대체되었습니다.)
* **Render phase는 중단/재개/폐기 가능**, **Commit phase는 중단 불가**
  → 렌더 도중 더 급한 입력이 들어오면 계산 중이던 트리를 버리고 다시 시작할 수 있음
* React 18/19에서는 `createRoot`를 쓰면 이 **동시성 렌더링이 기본값**입니다.
  (별도의 "Concurrent Mode"를 켜는 것이 아니라, 기능 단위로 선택해서 씁니다 — 자세한 내용은 3.9)

## 7. React DOM 처리 최적화 기법

| 기법                       | 설명                                 |
| ------------------------ | ---------------------------------- |
| `React.memo`             | 컴포넌트 props가 변하지 않으면 리렌더링 방지        |
| `useMemo`, `useCallback` | 함수나 값을 메모이제이션하여 불필요한 연산 제거         |
| Key 설정                   | 리스트 항목에 고유한 key를 설정해 diffing 효율 향상 |
| Lazy Loading             | 동적 import로 필요한 시점에만 컴포넌트 렌더링       |

## 8. 전통적인 DOM 처리와의 비교

| 항목        | 전통 방식 (Vanilla JS / jQuery)                        | React                                  |
| --------- | -------------------------------------------------- | -------------------------------------- |
| DOM 조작    | 직접 DOM API (`document.createElement`, `innerHTML`) | 가상 DOM 기반으로 최소한의 변경만 실제 DOM에 반영        |
| 이벤트       | 이벤트 리스너 직접 바인딩                                     | Synthetic Event 시스템 (버블링 최적화)          |
| 상태 기반 렌더링 | 수작업으로 DOM 업데이트                                     | 상태 변경 → Virtual DOM diff → 실제 DOM 업데이트 |
| 성능        | 손으로 최적화하면 가장 빠르지만 관리 부담이 큼                          | diff 비용이 추가되나 **평균적으로 충분히 빠름** + 자동 batching |

> React가 바닐라 DOM 조작보다 **원리적으로 빠른 것은 아닙니다.**
> React는 diff라는 추가 비용을 지불하는 대신, **어떤 DOM을 언제 고칠지를 사람이 관리하지 않아도 되게** 만듭니다.
> 얻는 것은 절대 성능이 아니라 **예측 가능성과 유지보수성**입니다.

---

## 결론

> React는 **Virtual DOM + Reconciliation + Fiber 아키텍처**를 통해 DOM을 **선언적으로, 효율적으로, 비동기적으로 처리**합니다.

* 전통 DOM 방식은 **명령형(Imperative)**, React는 **선언형(Declarative)**
* 실제 DOM은 **결과물일 뿐**, 모든 UI 상태 변화는 Virtual DOM의 변화를 통해 간접적으로 처리됨
